# 命令路由：规则快路径 + 模型兜底

> 状态：已实现（`src/game/router.ts`）。本文记录选型时的评测方法与结果，供评审、答辩引用。

## 结论

一句话由玩家说出来后，服务端要先判断它是哪一类命令。关键词表能覆盖常见说法，但覆盖不了自由表达；纯模型方案又太慢、会误判关键指令。所以采用混合路由：

- **快路径保留在本地**：动作词典、别名、ASR 同音、唤出词、开局、加入房间、战况这些确定性强的输入，仍由 `readCommand` 一次读成命令，零延迟、零模型调用。
- **规则认不出的句子交给决策模型**：把「这句话是哪一类命令」做成一道按阶段收窄的 choice 题，交给 Command Code 的 System One（决策模型 `typesafe/jev`）。菜单只包含当前阶段可能成立的命令，问句阶段与上一局结束之后都不含任何招式，因此问一句不会真的出招；打完一局的菜单里只留开局、开房、查询、玩法与闲聊。
- **回来还要核对那一局**：路由是异步的，模型返回后这一手带着开始思考时那一局的 id 进对局事务，取到锁再比对；期间重开、换房或对局过期就作废这一手，让玩家重说，不把旧指令落到新局上。开局与开房会改对局归属，也在动手之前核对当时那张桌子与那一局——否则刚开的新局会被重置，甚至把两个人正在打的房间一起撤掉。
- **关键词分流表已删除**：`src/game/questions.ts` 不再存在；判断「规则内还是规则外」不再靠词表，而是与其它命令放在同一道选择题里。
- **失败一律回退**：模型缺失、超时 1.5 秒、HTTP 异常、置信度低于 0.6、选项不在菜单内，都按「没听出来」处理，不消耗资源、不推进回合。

## 评测方法

- **语料**：64 条中文输入，人工标注期望结果。覆盖七种招式与口语说法、ASR 同音（如「公鸡」）、唤出咒语、战况查询、玩法、开局、开房、加入房间、规则外提问、闲聊与语气词。语料是自拟的，规模有限，结论只代表这类输入。
- **四套方案**：
  1. `rules`：只用 `readCommand` 的关键词与别名；
  2. `current`：`readCommand` + 原意图模型兜底（即 648e592 的线上行为）；
  3. `hybrid`：`readCommand` + 全命令模型兜底（本文实现的方案）；
  4. `model`：不用关键词表，每条都问模型。
- **模型与参数**：Command Code System One，`POST /provider/v1/systemone`，`model=typesafe/jev`，置信度阈值 0.6；请求的 `state` 里必须带原话（`utterance`），否则模型看不到输入。
- **测量**：单进程逐条调用，记录最终命令类型与耗时；每条独立请求，不含缓存与并发。
- **口径说明**：`hybrid` 与 `model` 两行用的是同一份全命令菜单（14 个选项、不区分阶段）测得的；当前实现按阶段收窄菜单（问句阶段只有查询/玩法/规则外，结束状态只有开局/开房/查询/玩法/规则外），选项更少，预期不低于表中的准确率，但未单独复测。

## 结果

| 方案 | 准确率 | 中位延迟 | p95 | 模型调用 | Token（输入 / 输出） |
| --- | --- | --- | --- | --- | --- |
| `rules` 关键词表 | 49/64 = 76.6% | ≈0 ms | — | 0 | 0 |
| `current` 关键词 + 意图模型兜底 | 56/64 = 87.5% | 0.14 ms | 1.03 s | 8 | — |
| `hybrid` 关键词 + 全命令模型兜底 | 59/64 = **92.2%** | 0.24 ms | 0.85 s | 8 | — |
| `model` 纯决策模型 | 58/64 = 90.6% | 794 ms | 1.55 s | 64 | 44,496 / 7,558 |

混合方案在准确率和延迟上都最好：大多数句子走本地快路径，只有 8 条落到模型；纯模型方案每条都要等约 0.8–1.0 秒。

## 未命中明细

- `rules`（15 条）：打他一下、摸他一下、试探一下、狠狠地打他、全力出拳、开大、把能量攒满（被读成战况）、稳住攒一下、憋个大招（被「大招」抢走）、挡住、我来挡、闪一下、推荐一部电影、上海明天天气、我有点无聊。
- `current`（8 条）：把能量攒满、憋个大招、挡住、我来挡、闪一下、推荐一部电影、上海明天天气、我有点无聊。
- `hybrid`（5 条）：把能量攒满→战况、憋个大招→大招、今天天气不错→规则外、随便聊聊→规则外、我饿了→规则外。
- `model`（6 条）：公鸡→没听清、共鸣斩破军→大招（应为普攻）、开打→普攻（会真的出招）、今天天气不错/随便聊聊/我饿了→规则外。

## 稳定性

同一句话连问 3 次，结果一致：

| 输入 | 期望 | 三次返回 |
| --- | --- | --- |
| 打他一下 | 普攻 | 普攻 / 普攻 / 普攻 |
| 挡住 | 格挡 | 格挡 / 格挡 / 格挡 |
| 开大 | 大招 | 大招 / 大招 / 大招 |
| 上海明天天气 | 规则外 | 规则外 / 规则外 / 规则外 |
| 今天天气不错 | 没听清 | 规则外 / 规则外 / 规则外 |

最后一行是纯模型方案把陈述句当成闲聊的典型例子，也是混合方案保留「陈述句不触发模型问答」这条边界的原因之一。

## 纯模型方案的三个代价

1. **延迟**：每条指令多等约 0.8–1.0 秒（p50 794 ms、p95 1.55 s），对语音出招的节奏是硬伤。
2. **关键指令误判**：ASR 同音（「公鸡」）、唤出咒语（「共鸣斩破军」被选成大招）、口语开局（「开打」被选成普攻）都可能错；后者会真的消耗能量出招。
3. **陈述句变闲聊**：「今天天气不错」「我饿了」「随便聊聊」被分到规则外，会触发一段闲聊回复。要不要让伙伴接话是产品取舍，技术上加几条例句规则很容易，但那又回到了关键词表。

## 为什么保留快路径

- 确定性输入不该为不确定性付出延迟：招式、开局、加入房间这类词表已经稳定覆盖，模型只会增加抖动。
- 关键指令需要确定性：咒语和 ASR 同音一旦被模型选错，直接消耗资源甚至输掉对局。
- 混合方案把模型的用途收窄到「规则确实认不出」的长尾，准确率反而比纯模型更高（92.2% 对 90.6%），延迟也可控。

## 局限

- 语料 64 条、自拟、单人标注，不代表真实玩家分布；真机试玩后应补充语料并重跑。
- 结果依赖 `typesafe/jev` 当前版本；模型升级或降级都可能改变数字。
- 只测了准确率与延迟，没有测成本；`model` 方案的 token 用量仅供量级参考。
- 未做真机朗读验收，也没有验证不同网络条件下的 p95。

## 复现

评测脚本与 64 条语料保存在仓库外（临时材料），重跑需要 `COMMAND_CODE_API_KEY` 与同样的语料。命令行形式：

```bash
COMMAND_CODE_API_KEY=... node --import tsx /tmp/eval-router.mts
```

如需长期维护，建议把语料与脚本整理进 `tools/eval/`，作为路由改动的回归门禁。
