# 技术亮点

> 面向评审与答辩的技术说明。产品侧亮点见 [README](../../README.md#项目亮点)，实现细节见[架构与设计决策](architecture.md)。

这套系统的技术难点不在「语音识别」或「大模型对话」，而在于三件容易做错的事：**一句话要能被听懂、一场对局只能有一个裁决者、一只住在硬件里的伙伴得先开口**。下面是我们在这三件事上的做法与代价。

## 1. 让「怎么说都算」：三层意图理解，模型只做选择题

产品承诺是「不用背口令」，技术上的反命题是：纯关键词表覆盖不足，纯模型又慢且会在关键指令上跑偏。

我们把判断拆成三层，按「便宜且确定」到「贵且模糊」依次调用，前一层认出来就不进后一层：

| 层 | 位置 | 认什么 | 耗时 | 为什么放在这一层 |
| --- | --- | --- | --- | --- |
| 规则快路径 | `src/game/command.ts` | 招式词表、别名、ASR 高频错写、唤出词、战况 / 玩法 / 开局 / 发起挑战 / 接受挑战 / 否定 / 歧义 | ≈0 ms | 确定性最强，错了也可预期 |
| 端侧同音 | `src/game/asr.ts` | 音节相同或只差一处声母/韵母的错字（「公鸡」→普攻）、整句口语简称（「开大」→大招） | 毫秒级 | 只解决「字被写错」，不解决「说的是别的意思」 |
| 决策模型 | `src/game/router.ts` + `llm.ts` | 这句话属于哪一类命令，在**按当前阶段收窄的菜单**里选一项 | 0.7–1.1 s | 兜住自由表达，永远排在最后、永远可回退 |

关键设计是把模型的任务从「理解游戏」降级成「做选择题」：菜单里只有当前阶段可能成立的命令，选项里**没有任何数值**。问句阶段与上一局结束后的菜单都不含招式，所以「重机是什么意思」不会真的出一手，打完一局的菜单只留开局、查询和闲聊。模型返回后仍要过服务端规则引擎，能量不够照样被拒。

代价与收益都量过。64 条人工标注语料、四套方案（详见[命令路由](command-routing.md)）：

| 方案 | 准确率 | 中位延迟 | 模型调用 |
| --- | --- | --- | --- |
| 只用关键词表 | 76.6% | ≈0 ms | 0 |
| 关键词 + 旧意图模型兜底 | 87.5% | 0.14 ms | 8 / 64 |
| **关键词 + 全命令决策模型兜底（现方案）** | **92.2%** | 0.24 ms | 8 / 64 |
| 纯决策模型，每条都问 | 90.6% | 794 ms | 64 / 64 |

混合方案在准确率和延迟上都优于纯模型：九成句子走本地快路径，一秒内只有少数句子需要一次模型往返。失败口径统一——模型缺失、超时、置信度低于 0.6、选项不在菜单内，一律按「没听出来」处理，**不消耗能量、不推进回合**，玩家只需要再说一遍。

## 2. 事实与话术分离：服务端出事实，平台出人话

伙伴的台词要像人，但战果不能像人一样随口说。

我们把一次调用的返回拆成两层：MCP 工具在 `content[].text` 里返回**一行 v2 事实 JSON**（`you`/`foe` 的生命值与能量、`round`、`pending`、`choices`、`need`、`events`、`deny`/`reason`），平台智能体再按人设把这句话演绎成台词。事实层只有一份、且由服务端生成；表达层可以千变万化，但必须保留战果、数字、归属、成功失败与胜负。

协议上刻意不用 `structuredContent`、也不放整局快照：一行 JSON 便于模型逐字读到数字，16 KB 上限超了就报错而不是截断——截断的真相比没有真相更危险。要画面时另走 `GET /state` 与 SSE `state` 事件，两套通道各管一件事。

反过来，表达模型「演过头」时服务端会拦：数字对不上、归属明显出错、宣布了还没发生的结果，就退回工具原文。这不是为了限制文笔，而是因为**一句谎言比一句平淡更贵**——玩家一旦听出「明明没打中却说打中了」，规则引擎攒下的信任就没了。

## 3. 职责分明：MCP 是插件，人设住在平台

公开工具只有两个：`game_say` 和 `wait_event`。平台智能体的原话固定调用一次 `game_say`，不自行分类、不在多个工具之间切换；服务端只负责理解、校验与裁决，不碰音频、不认识 TTS。

这个边界让服务端变成了可插拔的「规则内核」：同一份 MCP 服务可以挂进任何设定的智能体里——校园学长、傲娇精灵、中二解说员，甚至换掉整个世界观。人设由玩家自己创建和调整，**服务端一行代码都不用改**，而玩家的角色资产留在了平台上。

这也是粘性的技术来源：玩家养的不是一只会念台词的程序，而是一个「住在自己设备里、由自己定义」的角色。人设越像自己人，越舍不得换掉这台硬件。

## 4. 主动开口：用挂起代替轮询

语音硬件最尴尬的处境是：它只能被叫醒。伙伴永远在等你说话，就永远是个工具。

我们的做法是把「等待」做成一次挂起的调用而不是反复询问：`game_say` 的返回里带 `need`，为 `wait_guest`（等人进房）或 `wait_foe`（等对手出招）时，平台在播完即时话术后再调 `wait_event` 把这次请求挂住；对手真动了，服务端唤醒调用并**只交付这一次的事实**；纯超时则静默续等，不发声、不重复念旧账。一次挂起默认 290 秒、上限 300 秒，长到足够覆盖「等人进房」这种真实空档，又不必让客户端轮询。

于是伙伴可以在你想要的时候先说话：「对面还剩 2 点血，要不要现在开大？」——提醒发生在玩家开口之前，而不是「你问它答」。同一身份最多只有一个在途等待，新输入、换局、取消或终局都会中止旧链，避免两只嘴同时说话。

（这个思路由佘维军老师提供，再次感谢。实现上踩过的坑记在 [MCP 协议](mcp-protocol.md)。）

## 5. 一个裁决者：纯函数结算 + 按对局串行

- **规则集中**：伤害、能量、轮次、暴击闪避概率、胜负判定全部收在 `src/game/rules.ts`，调参只动一处；模型和客户端不能修改任何数值。
- **结算是纯函数**：`resolveTurn` 不改输入、返回新状态与事件，随机源可注入，固定 seed 与时间就能复现一局——这让回归测试和数值对拍成为可能。
- **写回要认桌**：对局的读改写走 `src/store/serialize.ts` 的 `BattleTransactions`，锁的钥匙是存储键（单人局是玩家键、双人局是挑战编号），写回前确认仍是同一对局、同一座位，对不上就丢弃并让玩家重说。
- **异步结果不落错桌**：模型路由是异步的，回来时这一手还带着「开始思考时的那一局」，进事务取到锁后重新核对；期间重开、换房或过期，这一手作废。开局与开房会改对局归属，也在动手前核对当时那张桌子——否则旧结果会把新局重置，甚至撤掉别人正在打的房间。

## 6. 无屏也是完整载体

载体能力在 context 层用请求头 `X-Linx-Display`（`screen` / `voice`）解析，不交给模型猜：有屏返回界面快照，无屏走补账（`catchUp`），把玩家不在场时错过的对手行动一次性补齐。两类设备消费的是同一批事实，不重复交付、也不各自造一套状态。

## 7. 对手 AI：模型只做选择，规则保证合法

单人局的对手由 JEV 决策模型担任（`src/game/enemy-jev.ts`）：服务端先按当前能量、大招是否已用、阶段是否合法把选项过滤成一个小集合，模型只回答「选哪个」。模型置信度低不作拒绝依据（这类决策模型的置信度常在 0.3–0.5 区间），超时或选了非法项就回退本地策略。

结果是：**AI 可以有风格，但不能作弊**。它看不到未结算的隐藏结果，也拿不到不存在的选项；接入模型后同一局面不再保证逐字复现，但每一条落地的动作都是合法的。

## 8. 我们刻意没做的

- 没有账号体系、数据库、多实例与容器编排：演示阶段优先双人闭环的稳定性，内存存储足够，也避免把未验证的复杂度带进现场。
- 没有把语音链路塞进规则层：规则与播报不反向依赖 HTTP 或 MCP，沙箱只通过 HTTP/MCP 使用服务，所以换载体不用改内核。
- 没有让模型自己算数：一次判定 0.5–1.3 秒，而规则引擎是微秒级；能用规则判的，绝不让模型猜。

这些取舍都记录在[架构与设计决策](architecture.md)里，需要扩展时再逐条翻案。
