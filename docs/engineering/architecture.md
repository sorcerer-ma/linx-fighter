# 架构与设计决策

## Agent目标链路与当前兼容实现

目标链路：ASR → 平台／沙箱Agent原话固定调用game_say → MCP理解、校验与裁决 → Agent按真实结果与人设表达 → TTS。提示词来自 [项目配置](../../config/linx-agent-prompt.md)。当前转发路径已收敛，表达适配器仅有假fetch测试；由于MCP仍只返回文本，没有可验证的完整演绎事实契约，实际回复暂使用工具原文，并标记awaiting-facts。

以下是游戏服务真实执行链路，Agent不在调用前自主选游戏工具：

```
玩家语音
  → 灵犀设备
  → 灵犀平台（唤醒 + ASR）
  → MCP 客户端：POST /mcp 直接发 JSON-RPC（Streamable HTTP），调 game_say(text=原话)
  → 本服务 mcp/tools.ts → GameService.say
      → command.ts 读成命令（招式 / 战况 / 玩法 / 开局 / 开房 / 加入房间 / 不该出手 / 认不出）
      → 招式找桌子（table.ts：单人局 / 房间号）并排进对局事务（serialize.ts）
      → 认不出时才问命令路由模型，回来在事务里核对还是当时那一局
      → 路由判为规则外的提问直接交给 chat.ts，不碰对局
      → engine.ts（结算）+ enemy.ts（AI）+ pvp.ts（双人视角）+ narrator.ts（播报）
  → 工具返回 text
  → 平台模型把 text 念给玩家

旁路（只读，不参与判断）：
  手机/浏览器页面 ← EventSource GET /events（SSE，局面变化即推）
  Agent 脚本       ← GET /state（当前视角快照）
  本地沙箱兼容模式：原话经 game_say；Agent转发模式：platform/agent.ts 同样原话固定game_say，表达不得再执行游戏。
```

关键点：**服务端是对局规则与战果的唯一事实来源**。服务端理解原话并校验合法性与裁决；Agent负责原话转发及基于工具结果的人设表达，不自行分类、推演或重做行动。

## 分层职责

| 层 | 文件 | 职责 |
| --- | --- | --- |
| 接入层 | `src/http/app.ts` | 两种 MCP 传输（Streamable HTTP / SSE）、设备上下文提取、调试接口 |
| 协议层 | `src/mcp/server.ts`、`src/mcp/tools.ts` | MCP Server 创建、工具注册与参数校验、异常兜底 |
| 编排层 | `src/game/service.ts` | 开局 / 出招 / 战况 / 说明：按命令分派，把一手交给所在的桌子，再写回并播报 |
| 桌子与事务 | `src/game/table.ts`、`src/game/serialize.ts` | 单人局与双人局共用的接口（存储键、座位、视角、等对手、补账给谁）与对局事务（排队、写回前校验） |
| 规则层 | `src/game/engine.ts`、`src/game/rules.ts` | 回合结算与全部数值，纯函数、随机数由 seed 派生 |
| 策略层 | `src/game/enemy.ts` | AI 对手的决策模型，只读公开视角、不掷随机数 |
| 问答层 | `src/game/chat.ts`、`llm.ts` | 回答规则外提问，调用语言模型并清成可朗读的短句 | 不动对局、不产出数值 |
| 联机层 | `src/game/pvp.ts` | 房间号、双人视角镜像与写回 |
| 表现层 | `src/game/narrator.ts` | 播报文案，只依赖对局状态与事件 |
| 命令与视图 | `src/game/command.ts`、`src/game/state.ts` | 把原话读成一条命令（招式 / 战况 / 玩法 / 开局 / 开房 / 加入房间 / 规则外问答 / 不该出手）与界面用的局面快照 |
| 存储层 | `src/store/battles.ts`、`src/store/rooms.ts` | 对局与房间的读写、过期清理 |

依赖方向自上而下，规则层不感知 MCP，因此可以用 `scripts/demo.ts` 脱离协议直接跑玩法。

## 设计决策

### 1. 同时支持 Streamable HTTP 与 SSE

平台文档描述的是 SSE（`GET /mcp` 建长连接 + `POST /mcp/message` 发 JSON-RPC），最初的实现只做了这一套。但联调时日志显示平台实际打过来的是 `POST /mcp` + `application/json`，直接发 JSON-RPC、没有 GET 建连，属于新版的 Streamable HTTP 传输，服务端返回 404，设备侧就报「服务器出错」。

所以两套传输都保留，按方法分流，互不影响：

| 请求 | 传输 | 处理方式 |
| --- | --- | --- |
| `POST /mcp` | Streamable HTTP | 无状态：每个请求建一个临时 `McpServer` + `StreamableHTTPServerTransport`，请求结束即释放，响应为普通 JSON |
| `GET /mcp`（或 `/sse`） | SSE | 有状态：一个连接一个会话，先推 `endpoint` 事件给出 POST 地址 |
| `POST /mcp/message` | SSE | 把 JSON-RPC 交给对应 SSE 会话，响应从 SSE 通道返回 |

两种传输共用同一份对局存储，因此「先 POST 建对局、再用另一种传输继续出招」也能接上。平台控制台里填 `https://<域名>/mcp` 即可，不依赖地址后缀是不是 `/sse`。

### 2. 对局归属键 = 设备 ID + 智能体 ID

平台每轮对话会给新的 `X-Linx-Session-Id`，如果按会话存对局，玩家换个话题回来就「失忆」了。所以：

- 有设备 ID：`<deviceId>#<agentId>`，断线重连、重开对话都能接上；
- 没有设备 ID 但有会话 ID：退化为 `session:<sessionId>`；
- 都没有：`anon:<连接级 UUID>`，只用于本地手工调试。

GET 建连时平台可能还没带设备头，POST 调用一定带，所以上下文在每次 POST 时刷新（`applyRequestContext`），已拿到的值不会被空值覆盖。

### 3. 存储先用内存，接口保持可替换

`BattleStore` 是一个 Map + 写入时顺带清理过期对局（不额外起定时器）。单实例部署足够；多实例或重启保留对局时，换 Redis 实现即可，`GameService` 不用改。

### 4. 工具返回纯文本，不返回 structuredContent

框架阶段没有设备动作（音效、换角色）的需求。返回纯文本对平台侧模型最稳，不需要它理解额外结构。以后要播报音效，再按平台文档在 `structuredContent.funcs` 里下发 `linx_play`，工具的 `content.text` 保持不变即可。

### 5. 随机数全部由对局 seed 派生

`engine.resolveTurn` 保持纯函数，暴击/闪避的随机数来自 `battle.seed` 的计数器（`rng.ts`），不散用 `Math.random`。这样同一 seed 能逐位复现，仿真对拍才有意义：`pnpm validate` 用 CPython 同款 MT19937 重跑 256,000 局，任何结算顺序或数值漂移都会报错。

### 6. 双人联机用「视角镜像」而不复制一套引擎

`Battle` 内部以 `mode: 'solo' | 'pvp'` 区分是否跑 AI。双人模式下，每个玩家读到的都是自己的视角（`pvp.viewAs` 把 `player`/`enemy` 互换），写回时再换回基准视角（`canonicalize`）。引擎结算逻辑只有一份，房间号与「对局键 → 房间」索引放在 `RoomStore`。

### 7. AI 是决策模型，不是随机权重

对手按「能斩杀优先、保大招、生命值安全时积攒能量、否则先避免致死再最小期望伤害」做效用打分（`docs/game/ai-enemy.md`）。它不掷随机数，所有随机性只来自引擎，因此 AI 变化不会破坏对拍。

### 8. 认不出招式不消耗回合

语音识别错误很常见（「攻击」被识别成「公鸡」）。此时推进回合会让玩家莫名损失生命值/损失能量，体验很差；正确的做法是提示可选招式、保持状态不变，让玩家重说一遍。

### 9. 没有对局时直接出招自动开局

玩家第一句往往就是「攻击」而不是「开始游戏」。自动开局避免了一次无意义的往返，播报里会说明「先给你开了一局」。

### 10. 每个 SSE 连接一个 McpServer 实例

`McpServer` 内部保存每个连接的协议状态（初始化、能力协商），多连接共用一个实例会串会话。所以 `createMcpServer()` 在 `GET /mcp` 里按连接创建。

### 11. 错误不外抛

工具内部异常统一转成 `isError: true` + 一句玩家能听懂的提示，并记 error 日志。协议层保持 202 正常返回，避免平台侧模型拿到看不懂的协议错误后乱编结果。

### 12. 命令路由、JEV 与对手决策

关键词表不再是分流手段。`readCommand` 保留动作词典、ASR 容错、唤出词、开局/加入房间/战况这些确定性的快路径；只有规则认不出、或这句话是问句但不能执行时，才把原话交给命令路由（`src/game/router.ts`）——模型网关的决策接口（`POST /systemone`，决策模型默认 `typesafe/jev-1.14`），把「这句话是哪一类命令」做成一道 choice 题。菜单按当前阶段收窄：无对局时只有开局等选项，等对手时只有查询/玩法/规则外，轮到应对时只有格挡/闪避/承受，上一局打完了只给查询/玩法/开局/规则外，问句阶段不含任何招式，因此问一句不会真的出招。模型返回选择与概率，置信度 ≥ 0.6 才采纳；它不产出数值、不改对局状态，但它说的必须是「当时那一局」——路由是异步的，等模型期间玩家可能已经重开，核对与作废的时机见第 18 条；超时 2 秒、HTTP 异常、返回越界都回退为「没听出来」，因此断网也能玩。规则与模型之间还有一层端侧同音纠错（`src/game/asr.ts`）：只用离线音节表比对，毫秒级，认出来就直接还原动作、不花模型往返；它只在轮到自己的出招/应对阶段生效，认出的动作仍要过引擎校验。为什么这样分三层、并附四套方案的准确率与延迟对比，见 [命令路由评测](command-routing.md)。未配 `API_KEY` 时模型层整层不启用，前两层照常工作。

对手的每次出招与应对也走 JEV（`src/game/enemy-jev.ts`）：本地先按能量与大招次数过滤出合法选项，把「当前局面 + 最近六条战报 + 玩家出招/应对计数 → 选哪个」做成选择题；战报只来自已结算的公开历史，模型据此判断局势与预判玩家下一步，但仍看不到未结算的隐藏信息（暴击、闪避结果只以历史形式出现）。模型只能从合法选项里选，超时 2 秒、HTTP 异常、选项越界都回退 `ENEMY_AI`，置信度与概率只写日志。模型只选动作，数值与胜负仍只在 engine 算。因为要等模型返回，`resolveTurn` / `advanceBattle` 是 async，但仍不改入参、返回新状态；同一 seed 不再保证复现，单测与 256,000 局对拍都注入本地 AI，不受影响。`ENEMY_AI=local` 可关闭这层。

规则外的提问由命令路由分出来：路由在「问句阶段」的菜单里可以选「规则外」，判中后原话交给 `src/game/chat.ts`；命中对局话题（战况、能量、大招次数、玩法等）的问题仍由本地规则或路由的 status/help 选项回答。上一局打完也不影响问答：结束状态的菜单里同样留着规则外，所以打完一局还能问天气、听段子，只是不能再出招；想接着打说「开始游戏」这类开局说法，或者让路由在结束状态的菜单里把「我还想接着玩」认成再来一局。问答请求模型网关的 `/chat/completions`（默认 `deepseek/deepseek-v4-flash`），系统提示限定它只答游戏之外的问题、不编造对局数值，回来再清洗成两句、60 字内。这条路径不读补账、不碰对局与房间；模型缺失、超时或异常都只回一句固定话术，错误不进协议层。

### 13. 原话透传：MCP 只做传输，判断在服务端

平台侧模型只拿到一个推荐入口 `game_say`：玩家说完话，它把原话一字不改地放进去。想干什么由服务端判断——`readCommand` 一次读成命令（同音误识别与唤出指令交给 `matchAction`，规则认不出时再问命令路由模型），后续分派只看命令类型。

这么做的原因：玩家一句话可能是出招、查战况、问玩法、开房，平台侧模型每多一个选择就多一次选错的机会；而判断依据（当前阶段、合法招式、对局状态）本来就在服务端手边。工具总数也因此稳在 5 个以内。

### 14. 状态流用 SSE，不用 WebSocket

手机/浏览器只需要**看**局面：回合制、每回合只有几次变化、唯一事实来源在服务端、方向是单向的服务端 → 页面。SSE 的 GET + 文本协议正好匹配这个形状，浏览器原生 `EventSource` 自带断线重连，服务端也不用手写心跳与重连状态机。WebSocket 只在未来出现「双向低延迟输入」（比如手机当手柄实时操作）时才值得引入。

页面由 `/api/config` 拿到 `eventsUrl` 后直连 `GET /events?device=&agent=`（服务端开 CORS）。只有一种情况退回沙箱同源代理 `/api/events`：页面是 HTTPS 而服务端还是 HTTP，混合内容会被浏览器拦下。

### 15. 沙箱是独立目录，走真实入口

`sandbox/` 不复用服务端内部函数，而是像平台一样发 HTTP、调 `game_say`。好处是沙箱能骗过自己的只有 bug——它跑通的链路就是玩家会走的链路；坏处是多一层进程，所以它只做模拟与展示，不参与游戏判断。

页面同源代理状态流的身份默认补 `agentId`（`deviceId#agentId` 才是对局键）；直连时页面必须自己带 `?device=` 与 `?agent=`，否则会查到 `device#default` 这局空对局。

### 16. 双人局错过的结算用「补账播报」

双人局里 A 出招后，A 的播报只能停在「等对手应对」；B 的应对在 B 自己的回合结算，那一声只念给 B。平台没有服务端主动播报能力（工具调用只能由平台侧模型在对话轮次内发起，`docs/xrobot-dev-spec/mcp/software-mcp.md` 里的下行 `funcs` 也只随工具响应下发），所以这段对 A 是静音。

做法：每次结算完（没有待应对的攻击），把镜像到另一方视角的过程记进 `EchoStore`（按 `deviceId#agentId` 存，`src/store/echoes.ts`）；该玩家下一次任何发言——出招、问战况都算——由 `GameService` 取走，拼在播报最前面：「刚才那一手。我强攻，对手格挡，掉3点生命值，剩15。」。取走即清空，换局与退房一起清掉，过期时间跟对局一致；攒多了只补最近两段，避免播报拖长。事件换视角用 `pvp.ts` 的 `mirrorEvents`，它只翻「谁做的」，伤害与损失生命值按原样。

不选另外两条路的原因：改演示话术治不了真机；改成双方声明后统一结算，会改动玩法与平台交互节奏，演示前不值得。

### 17. 载体能力用请求头协商，补账按需关闭

补账播报解决的是「没有屏幕」的终端：它听不到对方应招的结果，只能等他下次开口补一句。有屏客户端（沙箱网页、将来的手机页）随时能画出双方生命值、能量与大招，再念一遍「刚才那一手」就是重复信息。

做法：能力走请求头，不走工具入参。`X-Linx-Display: voice | screen`，缺省 `voice`——平台与硬件不会声明这个头，保持既有体验；沙箱页面由 `SANDBOX_DISPLAY=screen`（默认）声明自己是屏幕。`src/mcp/context.ts` 把它解析进 `DeviceContext.display`，`src/mcp/tools.ts` 翻译成 `SayOptions{catchUp}` 传给 `GameService`。

细节：`catchUp: false` 时补账仍然被 `EchoStore.take()` 取走，只是不拼进文本——避免队列越攒越长，也避免客户端换回语音终端时突然念一堆旧账。工具入参保持「只有玩家原话」，不把载体差异交回平台侧模型判断。

### 18. 对局状态的修改按对局串行，异步结果回来先校验

命令路由（超时 2 秒）与对手决策（超时 2 秒）都是异步的：等待期间玩家完全可能重开一局、退出房间，或者另一条请求已经完成了结算。旧的结算结果一旦直接写回，就会把新状态覆盖成旧快照。

做法：对局状态的读改写按对局串行——单人按对局键（`deviceId#agentId`）、双人按房间号；`src/game/serialize.ts` 的 `BattleTransactions` 在排队开始时取一份快照，写回时比对存储里还是不是同一个对象（对局每次结算都换新对象，对象身份就是版本号），对不上就丢弃这次结果并让玩家重说。座位也会变（换房、房主重开），所以写回前还要确认玩家仍坐在原来的座位上。规则层本身仍是纯函数，串行只发生在编排层，不改变 `engine.ts` 的语义。

模型路由比对手决策多一个窗口：它先等模型（这一步不占事务），认出招式后才排队，所以只在排队前比一次局面挡不住「重开抢在这中间排进队」——那一手会排在重开之后执行，核对时看到的已经是新局。做法是把路由时那一局的 id 跟着这一手带进事务，取到锁、加载对局之后再比对：对不上就按旧局作废，让玩家重说；当时还没有对局的句子记作 null，因此也不会因为带着招式就落到之后新开的局上。座位与房间归属由写回前的原位确认兜住（座位只会随房间变，换房就换了对局键）。

开局和开房比出招更危险：它们会改对局归属，模型回来时若已执行，刚开的新局会被重置，`dropRoom()` 还会把两个人房间里的那一局一起撤掉。所以这类命令也带着当时那张桌子与那一局过去，在真正动手之前（开局在取到对局钥匙之后、开房在同步执行的入口处）核对桌子与对局 id，对不上就作废这一手。查询与规则外问答只是回答当前局面，不走这道关。

### 19. 单人局与双人局共用一条出招流水线

同一个玩家的一手牌，在单人局和双人局里要走的步骤完全一样：认招、确认还在战斗、结算、写回、播报、补账。原先单人、双人各写了一遍，两份代码各自维护权限校验、等待提示和补账拼接，改一处忘一处的风险很高（PR #2 的两个并发问题就是从两条流水线的差异里漏出来的）。

做法：抽出一层「桌子」（`src/game/table.ts`），只回答流水线需要知道的几件事——这一手存在哪个键、我坐哪一边、我看到的是不是镜像、要不要等对手、错过的结算记给谁、写回前我还在不在原位。单人桌直接用玩家键、没有镜像也没有对手；双人桌用房间号，视角经过 `pvp.ts` 的镜像与还原。流水线只有 `service.ts` 里的 `playOnTable` 一条，两条路线的差异全部落在桌子实现里。

### 20. 一个玩家同一时间只在一个有效房间里

`RoomStore` 维护「对局键 → 房间号」，如果玩家换房时直接把索引改指新房，旧房间会挂着一个已经离开的加入者，旧对手还在那儿等人、甚至能把局面打下去，两个人对同一份状态各说各话。

做法：席位由房间存储一次认领（`RoomStore.claim`）：先验目标房间（存在、不是房主自己、未满），验不过就什么都不改；验过了才占座，并把玩家原来那间房交出来，由编排层连着那局对局与双方补账一起撤掉，原对手下次开口时已不在任何房间，只会另开一局单人局；只有换房前已经发出、还没执行到的旧请求会撞上「没找到房间」。加入失败（房间号不对、已满、对局已过期）则原房间与原有对局完全不动，玩家不会因为报错一次就被踢出对局。房主说「来一局」重开也走同一条清理路径。

### 21. 监控页只读，且嵌在服务里

演示现场需要看到「每个房间两边各剩多少血、多少能量、大招用没用」——这既能当场排障，也能解释 AI 为什么这么打。做法：`/admin` 与 `/admin/api/rooms` 直接查编排层快照（`buildAdminOverview` 遍历 `RoomStore.list()` 与 `BattleStore.list()`，两处存储为此加了只读 `list()`，枚举顺带清理过期项），不复用玩家视角接口。页面 HTML 以字符串常量内嵌在 `src/admin/page.ts` 里——生产镜像是只拷 `dist` 的，运行时没有 `public/` 可读。

只读、无写接口：页面上能做的只有看和刷新，避免现场误触改了对局。默认公开（演示时拿到地址就能看），`ADMIN_TOKEN` 配了才校验，按来源限速 120 次/分，`trust proxy` 设为 `loopback` 以便 nginx 反代后仍按真实来源计数。公开的代价是房间号一并暴露，而房间号就是加入凭证；这一点写在页面页脚与部署文档里，生产环境应配口令。

### 22. 指令归属先判「是不是自己说的」

没有屏幕的设备无法「确认给我」，两台机器又可能收到同一句话。服务端能做的是在解析最前面加两道闸：①回灌判定——这句话是不是自己刚才播报出去的（`src/game/crosstalk.ts` 认出结算、提示、房间、结局等句式），命中只回一个「嗯。」，同局 2 秒内不再开口，避免回灌→应答→再回灌；②座位口令——双人房里说「红方，普攻」标明替谁说，`ATTRIBUTION_MODE=strict` 才启用，带对方口令的直接静默且零变化，不带口令则照旧按轮次仲裁。

为什么不让确认流程也要求口令：语音反复确认两轮，玩家根本不会照做，体验比偶尔算错更差；口令只做「替谁说」的可选标签，「谁在说」这件事服务端拿不到（平台不把说话人写进工具入参），只能靠平台侧的一设备一智能体加声纹。取舍与平台配合见[多设备归属](../product/multi-device-attribution.md)与[平台语音能力](platform-voice-capabilities.md)。

## 扩展指引

- **加招式**：在 `types.ts` 的 `ActionId` 加枚举，在 `actions.ts` 加 `ActionMeta`（含中文名、口语别名、ASR 误识别与唤出指令），工具参数无需改动；数值加到 `rules.ts`，结算逻辑在 `engine.ts`，并补 `test/actions.test.ts` 与仿真对拍。
- **调数值**：只改 `src/game/rules.ts`，同步 `docs/game/game-design.md` 与 `test/fixtures/v02-validation.json`（跑 `pnpm validate` 会告诉你哪项漂了）。
- **加属性**（如护甲、连击数）：加在 `Fighter`，同步 `narrator.ts` 的播报、`engine.ts` 的初始值，并确认 `pvp.swapSides` 仍然成立。
- **换存储**：实现与 `BattleStore` 相同的 `get` / `set` / `delete` / `sweep` / `size`，在 `index.ts` 替换构造即可。
- **多实例部署**：除了换 Redis 存储，还要注意 SSE 连接与 POST 必须落到同一实例（会话粘滞），否则 POST 找不到本地 transport。若做无状态部署，需要把会话注册表也放进共享存储。
- **可观测性**：所有关键动作（连接建立/关闭、开局、出招、工具失败）都有结构化日志，接日志采集时按 `message` 字段建索引。
