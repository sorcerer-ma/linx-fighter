# 灵犀平台语音能力调研

本文回答五个直接影响接入方式的问题：**ASR 热词能不能配、音频能不能透传做自建 ASR、声纹能不能拿到「说话人是谁」、一设备一智能体拆不拆得开、唤醒与串音能不能缓解**，并单列一节评估「若走音频透传改造」的代价。

- 取证时间：2026-10-24（平台文档持续更新，以下结论以该日期的 46 个正文页为准）。
- 取证方式：官方文档站全量抓取（见附录 A），逐页检索关键词并摘录原文；**查不到的地方一律标「未确认」，不用推测补齐**。
- 文档站：<https://linx.qiniu.com/docs/xrobot/>
- 相关既有文档：[接入灵犀平台](linx-integration.md)。

## 1. 一页结论表

| # | 问题 | 结论 | 一句话依据 | 现在能不能动 |
| --- | --- | --- | --- | --- |
| 1 | ASR 是否支持热词/自定义词表 | **不支持** | 46 页文档「热词」「词表」「词典」命中 0；智能体配置里 ASR 只有情绪识别与混合语种两个开关 | 不能。继续走我们的端侧模糊匹配（`src/game/actions.ts`） |
| 2 | 音频透传 / 服务端自建 ASR | **平台侧不支持** | 「透传」通道只承载 JSON 业务消息；WS 协议没有音频旁路字段，上行给 MCP 的只有文本 | 平台侧不行。技术上只剩「整层替换」（改固件 OTA 地址 + 自建 WS/ASR/TTS），见第 5 节 |
| 3 | 声纹 V2 能否在 MCP 请求里拿到「说话人是谁」 | **拿不到** | 平台只注入 `X-Linx-Device-Id`/`-Agent-Id`/`-Session-Id` 三个头；声纹是平台内部门禁，不返回识别结果 | 只能当「只回应本人」的过滤开关用，不能做游戏身份 |
| 4 | 一设备一智能体是否可行 | **可行，有官方 API** | `PUT /v1/devices/{mac_address}/agent/{agent_id}` 直接把设备切到指定智能体 | 现在就能配，约 10 分钟/台 |
| 5 | 唤醒与串音能否缓解 | **部分可以** | 唤醒词在设备端、平台没有「邻近说话人」策略；唯一平台级杠杆是声纹门禁，且必须配合第 4 项的拆分才生效 | 拆智能体 + 声纹「仅回应已添加说话人」+ 播报侧规避 |

一句话概括：**平台给我们的是「一台设备 + 一个智能体 + 一段文本」，说话人身份和原始音频都不会流到我们这边。**

## 2. 逐项证据与原文摘录

### 2.1 ASR 热词：文档层面不存在这个能力

**结论：不支持，且不是「藏在控制台某处」的不支持——三个可能的入口逐一排除了。**

1. 智能体配置项逐字段检查（<https://linx.qiniu.com/docs/xrobot/api/agent>）。智能体 `extra` 里与语音识别有关的只有：

   ```json
   { "asr": { "disable_emotion": false, "enable_auto_lang": true } }
   ```

   原文对这两个字段的解释（<https://linx.qiniu.com/docs/xrobot/guide/agent-config>）：「3.4 语音识别配置 … 情绪识别：在语音服务支持时，尝试识别用户的说话情绪；混合语种识别：在语音服务支持时，自动判断输入语言」。**这就是控制台里语音识别相关的全部可配置项。**

2. ASR 引擎只是一个模型 ID，没有词表参数。智能体配置里的 `asrModelId` 示例值是 `ASR_DoubaoASR`（同组还有 `vadModelId: VAD_SileroVAD`、`voiceprintModelId: VOICEPRINT_3DSPEAKER`）。换引擎可以，往里塞词表不行；文档也没给出 ASR 模型的配置 schema（只有 `GET /v1/agents/models/llm` 一个模型列表端点，没有 ASR 的）。

3. 全站检索（附录 A）：「热词」0 页命中、「词表」0 页、「词典」0 页、「自定义词」0 页。「ASR」命中 5 页，逐页看完没有一处提到词表或识别偏置。

**对我们的直接影响**：`重机`→强攻、`硬航`/`长寿`→承受、`我要可党。`→格挡、`我要拍照`→大招这一类，只能继续在 `readCommand` 的别名与同音容错里消化，没有平台侧捷径。这也解释了为什么 63 条语料里仍然有一批漏网（`重机`、`硬航`、`我要可党`、`长寿`、`我要拍照`、三个「强化普攻」变体、`我要开大`）——错在识别层，不在解析层。

### 2.2 音频透传 / 服务端 ASR：平台侧没有这条路

**结论：平台不会把音频交给第三方，也不会把音频交给 MCP 服务。设备说什么，只有平台 ASR 知道。**

证据一：上行音频的唯一去向是平台 ASR（<https://linx.qiniu.com/docs/xrobot/platform/websocket>）。设备连上后发 `listen`，然后就是二进制音频帧：

> 「设备端 → 服务器（开始监听）`{"type":"listen","state":"start","mode":"auto"}` … 同时设备端开始发送二进制帧（音频数据）。服务端 → 设备端（ASR 结果）`{"type":"stt","text":"用户说的话"}`」

文档给出的协议字段里**没有**任何能让设备把这段音频同时发往别处的能力，也没有「自定义音频流」消息类型。

证据二：给 MCP 的只有文本（<https://linx.qiniu.com/docs/xrobot/mcp/software-mcp>）。原文只说工具调用与返回，上行入参由大模型填；「content 是数组，每个元素对应一段内容（text / image / audio 等），设备端会按顺序处理」——**audio 只出现在下行返回里**，是让设备"播"，不是把用户的"说"给我们。

证据三：设备端 MCP 工具也没有录音能力（<https://linx.qiniu.com/docs/xrobot/mcp/hardware-mcp>）。端侧可用工具只有 `self.get_device_status`、`self.audio_speaker.set_volume`（另有拍照类），**没有"把麦克风数据交出去"的工具**。

证据四：唯一的「透传」是业务消息透传，明确只走 JSON（<https://linx.qiniu.com/docs/xrobot/guide/third-app>）：

> 「透传消息模式下，灵矽AI平台对消息内容不做任何处理，直接透传。一旦透传，灵矽AI是不管里面具体内容的，直接copy转发。」

链路是 `设备 --JSON--> 平台 --JSON--> 第三方 SSE 服务`，消息类型只有 `report` / `reset` / `get` / `command`。

证据五：音频确实存在，但只能**事后**按需取，不能实时喂给 ASR（<https://linx.qiniu.com/docs/xrobot/api/chat-history>）。聊天记录字段里有 `audioUrl`（原文「需要签名后才能访问」，签名 URL 有效期 1 小时、需要登录 token），另有 `audioId`（「已废弃，始终为null」）。**这是回放通道，不是实时通道。**

### 2.3 声纹识别 V2：能力真实存在，但边界恰好卡在我们要的地方

<https://linx.qiniu.com/docs/xrobot/api/voiceprint-v2>

能力概要：

- 「声纹识别 V2 以 说话人（Speaker） 为核心管理身份信息。一个说话人可以设置一条默认声纹；智能体需要绑定 speaker_id 后，才会识别该说话人。」
- 接口齐全：建说话人 `POST /v1/speakers`；录声纹 `POST /v1/speakers/{speakerId}/voiceprint`（**必填 `audio_url`**，即"平台可访问的样本音频 URL"）；绑定到智能体 `PUT /v1/agents/{agentId}/speaker-config`（传 `speaker_ids` 数组）。
- 「当前每个说话人维护一条默认声纹。重新创建声纹会替换旧声纹。」「建议使用清晰、单人、无明显噪声的语音样本。平台会处理音频并保存声纹，接口响应不包含声纹特征向量。」

**限制一：不返回识别结果。** 文档开头写得很直白：「本文档只描述软件侧配置接口。声纹处理由平台内部完成，公开接口不会返回声纹特征向量。」没有 1:N 识别端点、没有阈值参数、没有实时识别回调、也没有「本句来自哪个 speaker」的查询接口。唯一暴露 speaker 身份的地方是长期记忆接口的**设备 MAC**（<https://linx.qiniu.com/docs/xrobot/api/longterm-memory> 的 `identifiers/{identify_id}` 以「终端用户身份标识（如设备MAC地址）」为键）。

**限制二：MCP 请求里没有 speaker 头。** <https://linx.qiniu.com/docs/xrobot/mcp/software-mcp> 原文：「在设备 WebSocket 会话中，平台调用智能体配置的云端 MCP 服务时，会自动携带以下 HTTP 请求头，无需经过大模型传值」，表格只有三项——`X-Linx-Device-Id`、`X-Linx-Agent-Id`、`X-Linx-Session-Id`；紧接着一句：「MCP 服务端从请求头读取上述标识，平台不会将其自动填入工具入参（arguments）。」全站 `X-Linx` 只在 `mcp/software-mcp` 出现，端侧 `mcp/hardware-mcp` 连这三个头都没有。

**限制三：身份只落到提示词层。** <https://linx.qiniu.com/docs/xrobot/guide/agent-config> 第 7 节：「修改影响：成功识别后，智能体可以结合说话人称呼和信息交流。」也就是说，平台识别出是谁之后，把称呼喂给大模型的上下文——**大模型知道，我们的 MCP 服务不知道**。想让它告诉我们，只能让模型把称呼塞进工具参数，那等于把身份判断交给模型，与本项目「身份由接入层解析，不放进游戏工具参数」的约束直接冲突。

**它唯一能替我们做的事：当门禁。** 「7.2 仅回应已添加说话人 … 开启：语音需要成功匹配当前智能体已添加的说话人，才能继续回答。未添加、录音质量不佳或识别失败，都可能导致不回应。」（控制台侧只读，实际修改走 `PUT /agents/{agentId}` 的 `extra.voiceprint.chat_only_enabled`。）这是"要么回要么不回"，服务端拿不到任何信号——但恰好可以用来压串音，见 2.5。

### 2.4 一设备一智能体：官方支持，且有专门的切换接口

**结论：可行。** 有两条路，硬件上走第一条：

1. **MAC → 智能体绑定**（<https://linx.qiniu.com/docs/xrobot/api/agent>）：

   ```
   PUT https://xrobo.qiniu.com/v1/devices/{mac_address}/agent/{agent_id}
   Body: {"disable_chat_history_migration": true}
   ```

   原文「将设备切换到目标智能体」。`disable_chat_history_migration` 默认 `false`，即把该 MAC 的全部聊天历史迁移到新智能体；请求体必须存在，否则 `code 400`；错误码 400/401/403/404/599。这是"把 2 号设备从共享智能体挪到自己的智能体"的现成手段。

2. **握手头 `X-Agent-ID`**（<https://linx.qiniu.com/docs/xrobot/platform/agent-voice-switch>）：「在 WebSocket 握手 Header 中传入 `X-Agent-ID` … 此参数决定当前连接使用哪个智能体配置。」这条路只对自研 WS 客户端有用，开源小智固件默认不带这个头，真机实际走的是第 1 条。

**为什么值得拆**（这是本次调研最有用的推论）：声纹绑定是**智能体级**的（`/v1/agents/{agentId}/speaker-config`）。目前两台设备共用 `447ae9ac06ee4120b004326aca796002`，两个人必须都绑到同一个智能体上，于是「仅回应已添加说话人」对串音毫无作用——两个人都"是主人"。拆开之后，A 设备的智能体只绑 A 的声纹，B 在 A 旁边说话时 A 设备会**不响应**，串音从"一定会被当成指令"降级为"可能被忽略"。

**副作用**（都是可控的）：聊天历史与长期记忆按智能体隔离；提示词、MCP 勾选、模型与音色要各配一份，后续改配置要改两处；`deviceId#agentId` 这个定位键仍然唯一（现在唯一性来自 deviceId，拆完来自两者），游戏侧不用改代码；平台明确「智能体更新角色配置后，需重启设备才能生效」，每次改完要重启。

### 2.5 唤醒与串音：能拨的旋钮只有设备端和门禁

先厘清责任划分：

- **唤醒词归设备端。** <https://linx.qiniu.com/docs/xrobot/guide/agent-config> 8.2：「唤醒词回复开关 … 它不修改设备的唤醒词，也不等于关闭设备本身的提示音。」控制台只能控制"唤醒之后要不要打招呼"。文档里也没有任何唤醒词定制接口（`api/device` 页检索「唤醒」「音频」0 命中）。
- **收音窗口由设备控制，不是平台控制。** `listen` 的 `state` 只有 `start`/`stop`/`detect`（<https://linx.qiniu.com/docs/xrobot/platform/websocket>），「表示设备端开始、停止录音监听」。**文档没有给唤醒后收音的默认时长**，也没有配置项——未确认。
- **平台没有"谁的声/谁在旁边"的会话策略。** 全站没有"邻近说话人""仅当前说话人""优先最近说话人"之类的描述。
- **回声/降噪没有文档。** 全站「AEC」「降噪」「回声消除」均 0 页命中（唯一的字面「回声」是「返回声纹」跨词巧合）。设备是否带 AEC、参数能否调，**未确认**，必须问平台。
- **平台侧可选的旋钮**：`listen.mode`（`manual` 手动 / `auto` 唤醒词触发 / `realtime` 全双工，检测到语音则打断）、`abort` 的 `reason: wake_word_detected`、`extra.goodbye.idle_timeout_seconds`（60~3600 秒，控制台初始 120）、8.2 的唤醒回复开关。注意控制台对空闲超时的说明：「实际判断还考虑会话中的音频等活动，不应理解为「只从用户最后一句话结束开始精确倒计时」。」

结合我们的实证（自家播报「对手一记普攻」「轮到你出招」「轮到我们了，大招。」被当玩家原话回灌），这类串音的成因是**设备在 TTS 播放尾巴/播放结束后仍在收音**，平台侧没有任何开关能直接消除，只能：

1. 拆智能体 + 声纹门禁（把"谁都能指挥"变成"只认主人"）；
2. 播报侧规避：长度压到两句以内（这是本项目既定要求），不要出现疑似唤醒词；
3. 真机上确认设备当前 `listen.mode`（这个值在聊天记录里以 `clientListenMode` 回显，见 `api/chat-history`），realtime 全双工会更容易自激，可考虑退回 auto。

## 3. 可执行配置清单

### A. 拆智能体：一台设备一个智能体（今天就能做，约 10 分钟/台）

1. 现有智能体「灵犀对决」留给 1 号设备（`e8:f6:0a:8c:56:6c`）不动；控制台复制它 → 新建第二个给 2 号设备（`e8:f6:0a:8b:f4:b4`），起名带玩家标识。新智能体里三样必须配好：对话模型（要支持 Function Call）、勾选同一个自定义 MCP（`http://111.62.156.213/mcp`）、提示词（照抄 [linx-integration.md](linx-integration.md) 第 5 节）。
2. 取新智能体的 `agent_id`（控制台可见，或 `GET /xiaozhi/agent/list`）。
3. 用平台 token 把 2 号设备切过去（1 号设备已绑在现有智能体上，不用动）：

   ```bash
   curl -X PUT "https://xrobo.qiniu.com/v1/devices/e8:f6:0a:8b:f4:b4/agent/<agentId-2>" \
     -H "Authorization: Bearer <token>" -H 'Content-Type: application/json' \
     -d '{"disable_chat_history_migration": true}'
   ```

4. 重启 2 号设备（平台明确「智能体更新角色配置后，需重启设备才能生效」）。
5. 验证：两台各说一句话让工具调用一次，服务端日志里应看到两台的 `X-Linx-Agent-Id` 不同，且房间号配对仍正常。

> 若担心演示效果，可先只拆一台做灰度；拆完若发现配置漏项，用同一个接口把设备切回共享智能体即可回滚。

### B. 声纹门禁：让 A 设备不再响应 B 的嘴（拆完再做，需真机验证）

1. 前置：控制台「记忆与隐私 → 聊天保存」选**「文本+语音」**，保存并让设备重连——否则拿不到录音样本。
2. 各自说一段（原文「尽量不少于 5 秒」「清晰、连续、背景安静」），在「声纹功能」里建说话人：填称呼（≤40 字符）与信息（≤120 字符）。
3. 每个智能体只绑自己主人的 speaker（`PUT /v1/agents/{agentId}/speaker-config`，`speaker_ids: [...]`）。
4. 打开「仅回应已添加说话人」（`extra.voiceprint.chat_only_enabled: true`）。
5. 验证与判据：A 说话→A 设备响应；B 在 A 设备旁说话→A 设备**不响应**；A 说话→B 设备**不应**误响应（这条最容易翻车，必须实测）。
6. 回滚：把 `chat_only_enabled` 置回 `false` 即可，秒级生效、无需重启（是否需重连未确认，建议同时重启一次设备）。

**建议先做完第 5 步再决定开不开**：原文已警告「未添加、录音质量不佳或识别失败，都可能导致不回应」，现场临时上手、没录过声纹的人大概率不在名单里——一旦开启，这些人说话设备会全程沉默。

### C. 提示词与播报侧（零成本，不依赖平台）

- 播报维持两句以内、不超过 60 字，减少尾音被收音的窗口。
- 在提示词中禁止模型复述玩家的原话，避免"你刚才说……"这种二次回灌。
- 保留服务端的"识别失败就请玩家再说一次"路径（已有），不要把没听清当成没说话。

### D. 不建议做的事

- 不要让模型把「说话人称呼」塞进 `game_say` 参数来传递身份——违反本项目身份解析约束，且模型会编。
- 不要用聊天记录的 `audioUrl` 做"事后转写"来补账——签名 URL 有效期 1 小时且需要登录 token，延迟以分钟计，对回合制对战没有意义。

## 4. 能力边界与风险

**平台能做 / 不能做**

| 事项 | 平台 | 说明 |
| --- | --- | --- |
| 唤醒、VAD、ASR、TTS | ✅ 平台全包 | 设备只负责收音与播放 |
| 把识别文本给我们的 MCP | ✅ | 只有文本，且由模型决定何时调 |
| 把设备/智能体/会话 ID 给我们 | ✅ | 三个 `X-Linx-*` 头 |
| 把"说话人是谁"给我们 | ❌ | 声纹只做平台内部门禁 |
| ASR 热词 / 词表 / 方言偏置 | ❌ | 文档 0 命中 |
| 音频旁路 / 自建 ASR 接入 | ❌ | 透传只走 JSON |
| 唤醒词定制 | ❌（文档层面） | 在设备固件侧 |
| 回声消除参数 | ❓ 未确认 | 文档 0 命中 |

**风险清单**

1. **声纹门禁的可用性是演示风险，不是技术风险。** 误拒（漏认）的直接后果是"设备不说话"，比串音更致命。必须在真机、在演示同一房间噪声条件下验证。
2. **拆智能体带来配置漂移**：两份提示词、两处 MCP 勾选，改一处忘另一处会出现"一台正常一台抽风"，且平台要求重启才生效。
3. **聊天记录没有说话人字段**（`api/chat-history` 只有 `chatType`、`content`、`macAddress` 等），所以事后复盘只能按设备分，不能按人分。
4. **计费没有 ASR/声纹分项**（<https://linx.qiniu.com/docs/xrobot/billing/resource-usage-billing>：只有「扣减倍率 = 1 + 大模型计时系数 + 音色计时系数」），所以无法从账单侧推断识别质量或调用量。
5. **文档与实测存在一处不一致**：`guide/mcp-store` 写「MCP 通信类型。当前只支持 SSE」，而我们实测平台走的是 Streamable HTTP `POST /mcp`（见 [linx-integration.md](linx-integration.md) 第 3 节）。以实测为准，但说明文档有滞后，任何"文档说不支持"的结论都建议再向平台确认一次。

## 5. 若走音频透传改造

> 前提：平台侧没有任何旁路能力（2.2 已证），所以"透传"这条路实际形态是**把中间层整个换掉**——设备连我们的服务，而不是"平台多转发一路给我们"。下面的评估按这个真实形态写。

### 5.1 需要改谁

| 层 | 要改什么 | 依据与可行性 |
| --- | --- | --- |
| 设备固件 | 把编译期常量 `OTA_URL` 从平台地址改指向我们的 OTA 服务；OTA 响应里由我们下发 `websocket.url` 与 token | 固件是开源小智固件，平台文档自己就指向 <https://github.com/xinnan-tech/xiaozhi-esp32-server/blob/main/docs/firmware-build.md>，其中写明 `config OTA_URL / default "https://api.tenclass.net/xiaozhi/ota/"`，示例改成自建地址。平台 OTA 文档（<https://linx.qiniu.com/docs/xrobot/platform/OTA>）也印证「设备的 WS 地址来自 OTA 响应」，不在设备本地写死。**可行，但需要 ESP-IDF 编译环境 + 烧录两台真机** |
| 平台配置 | 不需要改（等于绕过平台） | 代价：声纹、聊天记录、计费、OTA 固件升级、控制台全部失效 |
| 我们的服务端 | 新增长连接 WS 服务：收二进制 Opus/PCM 帧 → VAD/断句 → ASR → 游戏规则 → TTS → 回二进制音频帧；实现 `hello`/`listen`/`stt`/`tts`/`abort` 全套消息；接自建或云端 ASR、TTS | 协议已全部文档化（<https://linx.qiniu.com/docs/xrobot/platform/websocket> 第 3、4 节），平台还开源了参考客户端 <https://linx.qiniu.com/docs/xrobot/guide/client-demo>（C++/ALSA/PortAudio/Opus，16kHz 单声道、帧 60ms），服务端参考实现见 xinnan-tech/xiaozhi-esp32-server（Python）。**不是从零发明协议，是重写一个已开源的中间层** |

顺带一个已被验证的事实：协议里的音频参数是明确的——设备上行 Opus 16000/单声道/帧长 60ms，或 PCM 16000/16bit/小端/帧 20ms(320 字节)；服务端下行 TTS 帧 20/40/60ms，quality `medium` 时 24kbps。这决定了带宽与算力估算。

### 5.2 改造量与工期

按 1 人全职、有真机可烧录估算：

| 工作项 | 人日 | 说明 |
| --- | --- | --- |
| OTA 服务 + WS 服务骨架 + Opus 收发 | 2 | 协议字段齐全，可直接对着文档写；难点在帧节奏对齐 |
| VAD / 断句 / 打断 / 回声处理 | 2 | **最不确定**，回声处理若设备侧没有 AEC，软件侧补非常麻烦 |
| ASR 接入（含热词） | 1 | 云端 API 半天、自建 FunASR/SenseVoice 另加部署时间；**这是走这条路唯一的收益点** |
| TTS 接入 + 分句下发 | 1.5 | 需要按 `tts.state: start/sentence_start/stop` 正确切分，否则设备播放卡顿 |
| 与现有游戏/MCP 链路对接（身份、房间、并发） | 1 | 可以复用现有 `BattleTransactions`，身份从 WS 握手直取，比现在更简单 |
| 真机联调 + 回归 | 1.5 | 两台设备、噪声环境、断线重连 |
| **合计** | **9 人日**（乐观 6） | 不含固件编译环境搭建的折腾时间 |

### 5.3 延迟预期

结构上会发生这些变化（**未实测，不给毫秒数**）：

- 现在：设备收音 → 平台 VAD+ASR → 平台大模型决定调工具 → HTTP 到我方 MCP → 我方规则 → 平台 TTS → 设备播放。链路里有**两次跨网往返**（设备↔平台、平台↔我方服务）和一次**大模型决策**。
- 自建：设备收音 → 我方 WS → 我方 VAD+ASR → 我方规则（进程内）→ 我方 TTS → 设备。跨网往返少一次，且去掉了大模型决策这一跳（游戏意图本来就该由规则引擎判，不需要 LLM）。
- 代价：若 ASR 用云端 API，等于把"平台 ASR 一跳"换成"我们的 ASR 服务商一跳"，收益会被抵消；只有 ASR 与我们同机部署才可能净变快。

要拿到真数字，最小验证是 1 人日原型：本地起 WS 收 Opus → 解码 → 喂 ASR → 打印"首帧到首字"耗时，与现有链路的实际体感对照。

### 5.4 风险

| 风险 | 评估 |
| --- | --- |
| 合规 | 音频进入我方服务器后，我方成为音频处理者；对话音频可能含个人信息，**声纹属于敏感个人信息**，自建声纹需单独告知与同意。演示期即使不落盘也应声明 |
| 带宽 | 可忽略。上行 Opus 16kbps 级别、下行 medium 24kbps，合计约 3KB/s，一局 10 分钟不到 2MB/端 |
| 稳定性 | **最大风险**。现在 VAD、打断、回声、TTS 队列全部由平台兜底，改造后全部由我们负责；任何一项没做好，表现都比现在差 |
| 演示期回归 | 现有 281 项测试与真机验收全部基于平台链路；换链路等于推翻验证基线，38 小时内无法重建 |
| 功能回退 | 声纹门禁、聊天记录、控制台可视化、固件 OTA 升级全部失去，需要自建对应能力 |

### 5.5 结论：演示前（38 小时内）不做

理由按权重排序：

1. **工期差一个数量级**：9 人日 vs 剩余约 1.5 个自然日，且需要固件编译与烧录这类不可压缩的串行步骤。
2. **唯一收益点（热词）还没被证明值得**：我们先要确认热词真能把 `重机`/`硬航`/`可党`/`长寿` 这几类纠正过来，以及纠正后能否显著提升对局成功率——这是 1 天原型的结论，不是先做改造的理由。
3. **风险方向不对**：演示目标是"双人闭环稳定"，改造恰好把所有稳定性兜底换成我们自己写的代码。

建议节奏：本次演示继续用平台链路 + 第 3 节的 A/B/C 三项；演示后单独立项，先做 1 人日可行性原型（自建 WS + Opus 解码 + 带热词的 ASR，只打印识别结果，不接游戏），用真实语料对比"平台 ASR + 端侧容错"与"自建 ASR + 热词"的命中率，再决定是否投入完整的 9 人日。
