# 共鸣：闻声对决 · 语音与信息反馈

[返回产品设计总览](product-design.md)

日期：2026-10-24。状态：当前产品设计；未交付能力单独标明。

定义玩家的语音输入、伙伴的回应，以及有屏和无屏载体的战况反馈。当前实现与设计目标的区别见[总览说明](product-design.md)。

## 1. 语音输入与反馈设计

### 1.1 指令与阶段

| 所处阶段 | 可执行的战术选择 | 其它可用输入 | 不能产生的效果 |
| --- | --- | --- | --- |
| 无对局 | 无现成战斗；首句招式可自动开单人局 | 开房、加入、开始游戏、问玩法 | 随意闲聊不能创建战斗或消耗资源 |
| 等待加入 | 无 | 查询、房间管理、问玩法 | 未加入对手前不能发动攻击 |
| 轮到自己主动 | 普攻、强攻、大招、蓄力 | 查询、问玩法 | 不能一次执行多个行动 |
| 对手攻击待自己响应 | 格挡、闪避、承受 | 查询、问玩法 | 不能把主动攻击当作防守响应 |
| 自己攻击已锁定 | 无新的战术选择 | 查询、问玩法 | 不能替对手响应，不能按响应结果换招 |
| 等对手主动 | 无 | 查询、问玩法 | 不能抢先推进回合 |
| 已结束 | 无 | 查询结果、按当前流程重开 | 不能继续伤害或重复结算 |

房间管理可能结束旧对局，不属于无副作用查询，应与战斗选择分开说明。

### 1.2 理解失败与歧义

| 玩家原话或情况 | 产品要求 | 当前状态 |
| --- | --- | --- |
| “强攻”“猛攻”及已支持的 ASR 误识别 | 归一化为同一行动，仍校验阶段和能量 | 已实现，词表与自由表达效果需真机验证 |
| “我的大招还剩几次” | 查询，不扣能量或大招次数；应回答次数 | 已实现：通用状态播报回答双方大招剩余次数 |
| “不要大招” | 不执行，不把收手当成出招 | 已有拦截与提示，具体覆盖需持续验证 |
| “大招还是强攻” | 提示一次只选一种，不猜测执行 | 已有歧义拦截 |
| 没听清、未知说法、识别置信度不足 | 保持阶段，让玩家重说 | 已有兜底，不能用识别失败惩罚玩家 |
| 能量不足、大招已用、满能量蓄力 | 解释不合法原因，不改变战斗状态 | 已实现 |
| 慢请求返回时已换局或换房 | 不把旧结果写回新局，说明需要重说 | 已有串行处理与状态校验 |
| 网络重试带来重复行动 | 不允许同一已确认行动再次扣资源 | 作为验收要求；当前串行处理不等于完整的请求去重协议，尚需专项验证 |

### 1.3 伙伴播报原则

播报优先告诉玩家：行动是否生效、结果是什么、现在该谁说什么。采用短口语，常规回复以两句、60 字内为目标；补账与当前结果拼接后的总长度需单独检查，不能仅凭单段文案达标认定体验达标。

通用反馈的推荐话术示例，尚不代表现有实现已替换：

| 场景 | 示例 |
| --- | --- |
| 等待响应 | “对手强攻，我该格挡、闪避，还是承受？” |
| 识别失败 | “没听清，这次没出招。请再说一次。” |
| 查询大招 | “我还剩一次大招，对手已经用过。” |

伙伴可以有性格、回念唤出词和庆祝，但不能把“没躲开”说成“没听清”，不能提前宣布命中，也不能用角色表演盖住响应窗口。音效、灯效、动作不是当前已交付能力；如增加大招演出，主要演出应在防守选择完成后展开。

已确认无屏场景接受朋友互相提醒和玩家主动查询。反馈设计应让查询能帮助玩家理解局面，并支持面对面互动；不能将查询次数非零或朋友需要提醒直接视为失败。短反应的已确认方向与表达原则见下节。

### 1.4 伙伴短反应

**已确认方向**：伙伴回应主人、简短助威和友善挑衅都可以服务于线下面对面的热闹对战；短反应是必要的，但不增加播报量。这是产品表达方向，不代表现有播报已替换，也不意味着每个行动节点必须插入一句情绪台词。

**已实现**：单人局（对 AI）每回合的播报开头带一句自己的状态（「我14点生命值、1点能量，对手强攻还没结算」），玩家不用再问一遍战况；双人局不带，保持两句内的长度，双方数值从战况查询里看。补账播报也不带，避免攒了几条后每句都重复数字。

**已确认交流视角**：伙伴自己说话，与玩家交流，不是单纯的播报工具。本方伙伴以“我”表达自身行动、生命值、能量、大招和感受；“你”指正在指挥它的玩家，实际受击、闪避或被击倒的是伙伴，不是玩家。对方战斗角色仍称“对手”，不混同另一位真实玩家。现有服务播报已采用伙伴第一人称，并在战况查询中回答双方大招剩余次数；此表达视角不改变沙箱的本方／对手归属或内部状态字段，也不代表本文所有情绪台词与持续引导均已实现。

短反应属于本方战斗伙伴的表达，不是增加一个独立裁判或主持人。伙伴可以回应玩家指挥、为本方助威，或向局内对手伙伴喊“接招”；不能贬低真实玩家的人格、能力或身份，也不要求对方设备接话。以下内容只细化语音表达，不确定新的硬件动作或演出流程。

#### 融入现有反馈

- 在原本会返回的同一次回复中，用短反应替换机械措辞；不追加独立助威句、播报轮次、设备间自动对话或等待步骤。“接招”是表达，不开启新指令或响应流程。
- 保留行动是否生效、实际结算结果、必要数字和当前下一步；不能用情绪词占掉这些信息。攻击锁定时只能回应已出手，命中、暴击、减伤或闪避成功须等实际结算；失败不能说成成功，受伤仍要说清实际承伤。
- 交流要回应玩家指挥，也能在已有行动交接中请求下一步，例如“请指挥我出招”；玩家下一句话就是原有阶段的行动输入，不增加“确认后才能出招”的问答。伙伴表达自身行动和感受，同时说清实际战果；鼓励玩家不等于擅自选招、判定胜负或承诺下次必胜。
- “我／对手”分别对应本方与对方伙伴的数值归属；玩家是指挥与交流对象。交流仍依托现有请求与回复，不承诺持续聆听、主动唤醒或服务端主动发声。
- 替换后的完整回复应检查文字量与实际朗读时长，补账、唤出词和当前结果合并计算；不能只因单段低于原有两句、60字目标，就认定没有增加播报量。容纳不下时先保留必要事实与下一步，不另加播报来安放短反应。

#### 节点与措辞示意

以下话术体现伙伴自述与玩家交流的设计规范，现有服务播报已按第一人称调整；具体措辞不必逐字照搬，数字均以服务端实际结果为准，不得硬编码。节点表示可承载短反应的位置，不要求每次命中、受击或防守都表演。

| 节点 | 推荐话术 |
| --- | --- |
| 指令生效、攻击锁定 | 我出强攻，接招！等对手应对。 |
| 命中并结算 | 我强攻命中，对手承受掉5点生命值，剩8。等对手出招。 |
| 本方受击 | 我承受强攻，掉5点生命值，剩8。请指挥我出招。 |
| 闪避成功 | 我躲开强攻啦！请指挥我出招。 |
| 格挡后仍受伤 | 我格挡普攻，掉1点生命值，剩7。该我出招，听你的。 |
| 闪避失败 | 我没躲开强攻，掉5点生命值，剩3。请指挥我出招。 |
| 大招锁定 | 我放大招，接招！等对手应对。 |
| 获胜 | 我赢了，击倒对手啦！ |
| 失败 | 我被击倒了，这局输了。 |

大招的情绪强度不能提前暗示必然命中或获胜，也不能把一次使用的成本或次数提示挤掉；结算时仍依实际命中、闪避或暴击结果表达。终局短反应不新增再战流程，不将庆祝或失落反应解释成自动重开或要求玩家安慰、确认。

### 1.5 分阶段上手提示

**已确认方向**：直接双人上手、练习自选；规则按当前阶段逐步提示。首次需要的信息与具体流程由[玩家旅程](player-journey.md#31-首次与朋友开打一局)维护，本节维护表达边界。演示采用玩家主动开启、仅本局有效的简单引导，不做自动首次识别或跨局记忆；持续引导尚未实现或验收，示例不能当成现有能力。

- 玩家开启本局引导后，首次主动先介绍普攻、强攻及1点能量、2点能量成本；其他合法行动仍可用，不将短提示解释成限制招式。首次响应介绍格挡、闪避、承受及与进攻共享能量，响应结束说明同一玩家可以继续指挥主动行动。
- 沿用伙伴第一人称交流，把阶段提示融入现有回复；必要数字、实际结果和下一步优先，不要求玩家额外说“知道了”或确认。首次必要规则提示与日常短反应不同，不能每局、每次状态查询都重复完整教学，也不假定持续聆听或跨设备主动通知。
- 提示的完整回复仍须检查文字量与实际朗读时长，不能叠加教程、补账和情绪句后仅按单段长度宣称达标；不新增时长阈值。只需本局的启用与阶段已提示标记，相关首次阶段提示后不因查询重播；关闭则恢复日常短反馈。不另设基于局数、时间或概率的触发规则。
- 错误恢复给当前阶段与资源下可执行的选择；识别失败、非法行动不扣资源或推进阶段。网络请求结果不确定时先核实局面，不把重复攻击当通用恢复方式；文档要求不等于已实现完整请求去重。

以下是建议措辞，不是固定台词，也不是当前服务已返回的内容；能量和阶段仅为说明所设，实际回复以服务端为准：

| 情况 | 恢复示意 |
| --- | --- |
| 主动阶段3点能量，误说大招 | “我只有3点能量，大招要4点能量。普攻、强攻或蓄力，听你指挥。” |
| 需要响应且有足够能量，却说强攻 | “对手这招还没结算，我得先应对。格挡、闪避，还是承受？” |
| 没听清 | “没听清，这次没出招。请再说一次。” |

识别失败示例中的“没出招”不适用于请求可能已成功、只是回复丢失的情况；后者应先查战况。零能量自动承受时也不能继续提示玩家消耗能量防守。已有“怎么玩”是一次性通用帮助，不切换持续引导，也不据此承诺新增精准规则问答。持续引导开关尚未实现，不能将示意写成已支持的口令。

## 2. 公开信息与载体差异

双方伙伴的生命值、能量、大招剩余次数，以及轮次、当前行动方和待响应攻击，属于玩家理解战况所需的信息。暴击和闪避结果在结算后公开，不能在对手选择响应前泄露。

| 信息 | 有屏载体 | 无屏载体 |
| --- | --- | --- |
| 双方生命值、能量 | 现有沙箱通过快照和状态流展示 | 当前可查战况 |
| 大招剩余次数 | 状态快照已包含 | 战况播报回答双方剩余次数 |
| 谁该主动或响应 | 当前状态及待响应攻击 | 每次结算回复末尾都会说明该谁出招，查询战况也会给出；未识别等分支只提示当前能说什么 |
| 对方操作后变化 | 状态流更新 | 当前等玩家下一次发言补账；问玩法等分支的补账覆盖需专项验收 |
| 第三轮起的增伤 | 玩家需要能理解伤害为何变高 | 现有播报会在部分回合提示，是否足够需试玩确认 |

无屏设备还有一个只有硬件才有的问题：两台机器靠得很近时，一句话可能被隔壁机器收走，界面上的「确认」也不存在。归属判定、座位口令与平台侧声纹的配合见[多设备归属](multi-device-attribution.md)，这里不重复。

`screen` 与 `voice` 是当前服务的载体能力区分。有屏客户端关闭补账播报，自行呈现状态；无屏设备默认保留补账。屏幕存在不代表玩家一直看屏幕，试玩需观察是否会漏掉关键结果。有屏伙伴设备对战时，正面小屏朝向对手，背面朝向主人，背面只有外壳与指示灯、没有屏幕。语音是主人获得指令接收或需要重说、行动战果、轮转与胜负等既有必要信息的主通道，不能被正面表情动作或背面灯效替代。沿用现有短反馈与主动查询，不增加重复播报或每阶段额外确认；不能因为手机双视图可见正面就删减真实硬件所需语音。手机模拟的正背双视图是同一本方设备的观察视角，不代表硬件有双面屏，详见[手机模拟硬件演示](mobile-demo-design.md)。

本节有屏信息描述的是现有沙箱能力，不是手机演示的完整视觉设计。已确认手机演示由两人各用一部手机、语音指挥，无需触控出招，仅在硬件不足时补充演示；当前手机演示先以伙伴表情和硬件外观为主，不展开全身动作。“无需触控出招”仅定义战斗输入，不延伸定义系统级授权或启动交互。

伙伴是住在硬件里的独立角色，第一人称表达属于伙伴，不将硬件外壳视为战斗角色。手机当前以表情为主，防御可用最小局部小手举盾，不展开复杂全身动作；此前允许的模拟角色动作不意味着实体设备具有同样的机械动作，也不是本版必须展示的内容。外部指示灯与简单小屏幕是长期硬件方向；小屏与手机模拟以伙伴形象、表情为主，状态信息为辅，营造伙伴感。手机画面以伙伴为主角，硬件外观作为承载背景或边框；模拟震动只让画面中的硬件短暂晃动，不要求手机实际震动，也不承诺实体硬件具备震动能力。本次无屏演示路径保持不变；具体边界见[手机模拟硬件演示](mobile-demo-design.md)。
