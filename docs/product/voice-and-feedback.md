# 共鸣：闻声对决 · 语音与信息反馈

[返回产品设计总览](product-design.md)

日期：2026-10-24。状态：产品初稿，沿用 v0.1 的现状与建议标记。

定义玩家的语音输入、伙伴的回应，以及有屏和无屏载体的战况反馈。现有能力、建议设计与待决策的口径见[总览说明](product-design.md)。

## 1. 语音输入与反馈设计

### 1.1 指令与阶段

| 所处阶段 | 可执行的战术选择 | 其它可用输入 | 不能产生的效果 |
| --- | --- | --- | --- |
| 无对局 | 无现成战斗；首句招式可自动开单人局 | 开房、加入、开始游戏、问玩法 | 随意闲聊不能创建战斗或消耗资源 |
| 等待加入 | 无 | 查询、房间管理、问玩法 | 未加入对手前不能发动攻击 |
| 轮到自己主动 | 普攻、强攻、大招、蓄力 | 查询、问玩法 | 不能一次执行多个行动 |
| 对手攻击待自己响应 | 格挡、闪避、承受 | 查询、问玩法 | 不能把主动攻击当作防守响应 |
| 自己攻击已锁定 | 无新的战术选择 | 查询、问玩法 | 不能替对手响应，不能按响应结果换招 |
| 等对手主动 | 无 | 查询、问玩法 | 不能抢先推进回合 |
| 已结束 | 无 | 查询结果、按当前流程重开 | 不能继续伤害或重复结算 |

房间管理可能结束旧对局，不属于无副作用查询，应与战斗选择分开说明。

### 1.2 理解失败与歧义

| 玩家原话或情况 | 产品要求 | 当前状态 |
| --- | --- | --- |
| “强攻”“猛攻”及已支持的 ASR 误识别 | 归一化为同一行动，仍校验阶段和真气 | 已实现，词表与自由表达效果需真机验证 |
| “我的大招还剩几次” | 查询，不扣真气或大招次数；应回答次数 | 已阻止误出招；现有通用状态播报未专门回答大招次数，仍有信息缺口 |
| “不要大招” | 不执行，不把收手当成出招 | 已有拦截与提示，具体覆盖需持续验证 |
| “大招还是强攻” | 提示一次只选一种，不猜测执行 | 已有歧义拦截 |
| 没听清、未知说法、识别置信度不足 | 保持阶段，让玩家重说 | 已有兜底，不能用识别失败惩罚玩家 |
| 真气不足、大招已用、满真气蓄力 | 解释不合法原因，不改变战斗状态 | 已实现 |
| 慢请求返回时已换局或换房 | 不把旧结果写回新局，说明需要重说 | 已有串行处理与状态校验 |
| 网络重试带来重复行动 | 不允许同一已确认行动再次扣资源 | 作为验收要求；当前串行处理不等于完整的请求去重协议，尚需专项验证 |

### 1.3 伙伴播报原则

播报优先告诉玩家：行动是否生效、结果是什么、现在该谁说什么。采用短口语，常规回复以两句、60 字内为目标；补账与当前结果拼接后的总长度需单独检查，不能仅凭单段文案达标认定体验达标。

建议文案示例（不代表已替换现有文案）：

| 场景 | 示例 |
| --- | --- |
| 指令锁定 | “我出强攻，等对手应对。” |
| 等待响应 | “对手强攻，我该格挡、闪避，还是承受？” |
| 识别失败 | “没听清，这次没出招。请再说一次。” |
| 闪避失败 | “我没躲开，掉5点气血。请指挥我出招。” |
| 查询大招 | “我还剩一次大招，对手已经用过。” |

伙伴可以有性格、回念唤出词和庆祝，但不能把“没躲开”说成“没听清”，不能提前宣布命中，也不能用角色表演盖住响应窗口。音效、灯效、动作不是当前已交付能力；如增加大招演出，主要演出应在防守选择完成后展开。

已确认无屏场景接受朋友互相提醒和玩家主动查询。反馈设计应让查询能帮助玩家理解局面，并支持面对面互动；不能将查询次数非零或朋友需要提醒直接视为失败。短反应方向已确认，具体称呼、性格、台词与演出仍待讨论，详见下节。

### 1.4 伙伴短反应

**已确认方向**：伙伴回应主人、简短助威和友善挑衅都可以服务于线下面对面的热闹对战；短反应是必要的，但不增加播报量。这是产品表达方向，不代表现有播报已替换，也不意味着每个行动节点必须插入一句情绪台词。

**已确认交流视角**：伙伴自己说话，与玩家交流，不是单纯的播报工具。本方伙伴以“我”表达自身行动、气血、真气、大招和感受；“你”指正在指挥它的玩家，实际受击、闪避或被击倒的是伙伴，不是玩家。对方战斗角色仍称“对手”，不混同另一位真实玩家。这是后续反馈文案的设计原则，尚未修改现有服务返回、沙箱显示或状态字段。

短反应属于本方战斗伙伴的表达，不是增加一个独立裁判或主持人。伙伴可以回应玩家指挥、为本方助威，或向局内对手伙伴喊“接招”；不能贬低真实玩家的人格、能力或身份，也不要求对方设备接话。以下内容只细化语音表达，不确定新的硬件动作或演出流程。

#### 融入现有反馈

- 在原本会返回的同一次回复中，用短反应替换机械措辞；不追加独立助威句、播报轮次、设备间自动对话或等待步骤。“接招”是表达，不开启新指令或响应流程。
- 保留行动是否生效、实际结算结果、必要数字和当前下一步；不能用情绪词占掉这些信息。攻击锁定时只能回应已出手，命中、暴击、减伤或闪避成功须等实际结算；失败不能说成成功，受伤仍要说清实际承伤。
- 交流要回应玩家指挥，也能在已有行动交接中请求下一步，例如“请指挥我出招”；玩家下一句话就是原有阶段的行动输入，不增加“确认后才能出招”的问答。伙伴表达自身行动和感受，同时说清实际战果；鼓励玩家不等于擅自选招、判定胜负或承诺下次必胜。
- “我／对手”分别对应本方与对方伙伴的数值归属，向玩家说“请指挥我”时不能转成“你掉血”。交流仍依托现有请求与回复，不承诺持续聆听、主动唤醒或服务端主动发声。
- 替换后的完整回复应检查文字量与实际朗读时长，补账、唤出词和当前结果合并计算；不能只因单段低于原有两句、60字目标，就认定没有增加播报量。容纳不下时先保留必要事实与下一步，不另加播报来安放短反应。

#### 节点与措辞示意

下表以旧旁白视角作对照，右列体现已确认的伙伴自述视角；两列都只是文案示意，不是现有实现的逐字记录，也不是已锁定台词。左列将“你”当战斗角色的写法不再作为后续文案设计目标。数字只是假设该次服务端实际返回相同结果；实现不能硬编码这些数值。节点表示可承载短反应的位置，不要求每次命中、受击或防守都表演。

| 节点 | 旧旁白视角示意（对照） | 伙伴自述与交流示意 |
| --- | --- | --- |
| 指令生效、攻击锁定 | 你一记强攻已出手，等对手应对。 | 我出强攻，接招！等对手应对。 |
| 命中并结算 | 你一记强攻，对手承受，掉5点气血，剩8，等对手出招。 | 我强攻命中，对手承受掉5点气血，剩8。等对手出招。 |
| 本方受击 | 对手一记强攻，你承受，掉5点气血，剩8，轮到你出招。 | 我承受强攻，掉5点气血，剩8。请指挥我出招。 |
| 闪避成功 | 对手一记强攻，你闪开了，轮到你出招。 | 我躲开强攻啦！请指挥我出招。 |
| 格挡后仍受伤 | 对手一记普攻，你格挡，掉1点气血，剩7，轮到你出招。 | 我格挡普攻，掉1点气血，剩7。该我出招，听你的。 |
| 闪避失败 | 对手一记强攻，你没躲开，掉5点气血，剩3，轮到你出招。 | 我没躲开强攻，掉5点气血，剩3。请指挥我出招。 |
| 大招锁定 | 你一记大招已出手，等对手应对。 | 我放大招，接招！等对手应对。 |
| 获胜 | 你击倒了对手，赢了这一局。 | 我赢了，击倒对手啦！ |
| 失败 | 你被对手击倒了，输了这一局。 | 我被击倒了，这局输了。 |

大招的情绪强度不能提前暗示必然命中或获胜，也不能把一次使用的成本或次数提示挤掉；结算时仍依实际命中、闪避或暴击结果表达。终局短反应不新增再战流程，不将庆祝或失落反应解释成自动重开或要求玩家安慰、确认。

### 1.5 候选细化与待讨论项

以下是下一步可评估的建议，尚未确认具体规则：

| 事项 | 建议方向 | 尚待讨论的边界 |
| --- | --- | --- |
| 称呼与性格尺度 | 用“稳住”“漂亮”“接招”等易听懂的短表达体现伙伴感 | 是否在实际台词中称呼“主人”，以及鼓励、挑衅的具体语气；不预设固定性格 |
| 压缩与重复控制 | 减少同一句反复出现；补账较长时优先让当前结果易懂，避免重复表演旧事件 | 何时使用或省略、是否采用台词变体；不设连续次数、触发概率或固定频率 |
| 理解或执行失败 | 建议识别失败、非法行动、查询信息缺口等回复先清楚说明问题与可行下一步，不夹挑衅 | 是否统一省略这些回复中的情绪反应；不把本建议写成新增强制流程 |

细化后应比较完整回复的事实保留、长度和朗读效果，观察短反应是否帮助玩家感到与伙伴共同作战、是否挤占朋友间说话的空间；具体试验门槛与实现方式尚未确定。

## 2. 公开信息与载体差异

双方伙伴的气血、真气、大招剩余次数，以及轮次、当前行动方和待响应攻击，属于玩家理解战况所需的信息。暴击和闪避结果在结算后公开，不能在对手选择响应前泄露。

| 信息 | 有屏载体 | 无屏载体 |
| --- | --- | --- |
| 双方气血、真气 | 现有沙箱通过快照和状态流展示 | 当前可查战况 |
| 大招剩余次数 | 状态快照已包含 | 应可按需获知；当前播报存在[理解失败与歧义](#12-理解失败与歧义)中的缺口 |
| 谁该主动或响应 | 当前状态及待响应攻击 | 通过回复或查询获知，不能假设会主动播报 |
| 对方操作后变化 | 状态流更新 | 当前等玩家下一次发言补账；问玩法等分支的补账覆盖需专项验收 |
| 第三轮起的增伤 | 玩家需要能理解伤害为何变高 | 现有播报会在部分回合提示，是否足够需试玩确认 |

`screen` 与 `voice` 是当前服务的载体能力区分。有屏客户端关闭补账播报，自行呈现状态；无屏设备默认保留补账。屏幕存在不代表玩家一直看屏幕，试玩需观察是否会漏掉关键结果。

本节有屏信息描述的是现有沙箱能力，不是手机演示的完整视觉设计。已确认手机演示由两人各用一部手机、语音指挥，无需触控出招，仅在硬件不足时补充演示；展示突出伙伴形象、动作和真实硬件的样子。硬件产品、造型、布局及展示细节留待后续讨论；系统级授权与启动交互尚未确定，不由“无需触控出招”推定。
