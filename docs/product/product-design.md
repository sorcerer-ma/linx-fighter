# 共鸣：闻声对决 · 产品设计 v0.1

日期：2026-10-24。状态：供实现对齐与首次试玩评审的产品初稿。

本文定义玩家体验、产品范围和验收方式，不重复维护战斗数值。当前实现基线为已合并 PR #2 的 `2789c96`；“现有能力”指仓库实现和已有验证记录，不代表灵犀真机已经验收。“建议设计”与“待决策”不作为已确认需求。

## 1. 产品定位

共鸣：闻声对决是面向支持灵犀的硬件设备的语音对战游戏。硬件是玩家的战斗伙伴：玩家通过与自己的伙伴对话，指挥它与另一名玩家控制的伙伴战斗，击倒对手取得胜利。

玩家负责进攻、防守与资源取舍，伙伴负责接收指令、回应玩家和演绎战况。服务端维护唯一对局与裁决结果，伙伴不能凭角色性格擅自替玩家出招、修改伤害或编造胜负。

核心体验：**“我指挥自己的伙伴，和朋友的伙伴打一场听得懂、能决策的战斗。”**

对外产品围绕硬件伙伴展开；网页和手机沙箱是设备替身，用于开发、试玩和无硬件演示，沿用同一套游戏服务。单人 AI 对手提供练习与独自体验的入口。

## 2. 首轮玩家与场景

| 场景 | 玩家想完成的事 | 产品需要支持的体验 |
| --- | --- | --- |
| 两位朋友面对面 | 各自指挥一台设备，打一场并分出胜负 | 明确配对、谁先手、当前谁出招或应对、结果是什么 |
| 初次接触玩法 | 不看长说明也能开始尝试 | 提供短指令和阶段提示，错误输入可重说 |
| 一个人练习 | 熟悉进攻、防守和真气使用 | 用单人 AI 局走通战斗，明确对手为 AI |
| 演示或开发 | 不依赖实体设备复现一整局 | 沙箱多窗口或脚本走真实输入和结算链路 |

首轮以同一空间内的双人对战为主要验收场景，不预设年龄、设备屏幕或既有游戏经验。远程使用体验、陌生人匹配和长期留存暂不作为本轮验证目标。

## 3. 体验目标与判断依据

| 目标 | 可观察的结果 | 验证边界 |
| --- | --- | --- |
| 有指挥伙伴的感觉 | 玩家能将自己的话与伙伴行动、结果对应起来 | 真人访谈和观察，不能用模型调用成功率代替 |
| 知道何时该说什么 | 能区分主动、响应、等对手和结束 | 分别记录首次体验与熟悉后的阶段误判 |
| 能作资源决策 | 理解进攻和响应共享真气，知道大招有次数成本 | 询问玩家为何蓄力、格挡、闪避或主动承受 |
| 战斗结果可信 | 双方看到同一结果，语音查询不触发攻击 | 服务回归与双端对照，再做真机验证 |
| 节奏适合短时对战 | 多数对局在 3～5 个完整回合结束，播报不遮挡下一次选择 | 回合目标沿用早期设计；实际分钟数尚未确定 |

完整回合是双方各完成一次主动行动，不是一次说话。没有强制五轮结束规则。既有 256,000 局模拟中 87.53% 在 3～5 轮结束，但启发式策略池不能证明真人公平性；局部先后手差异与后期闪避集中仍需观察，详见[早期测试验证](../archive/v0.2/test-validation.md)。

## 5. 玩家旅程

### 5.1 进入与选择模式

玩家进入智能体后，需要知道“我可以指挥伙伴战斗”，以及单人练习和双人对战的入口。现有语音中，“开始游戏”开单人局，“开房间”开双人局；不要用同一条无说明的“开始”按钮暗示它一定会加入真人对战。

建议首次引导文案：“我是你的战斗伙伴。说开房间和朋友对战，或说开始游戏练习。”这是建议文案，尚不代表已经加入平台欢迎语。

没有对局时直接说出可识别的招式，当前会自动创建单人局并尝试执行；伙伴需要说明已经开局。双人场景应先明确开房或加入，避免把练习误认为已连接朋友。

### 5.2 建房与加入

1. A 说“开房间”，获得四位房间号，伙伴说明等待另一位玩家加入。
2. A 把号码告诉 B；B 对自己的设备说“加入房间1234”（以实际号码替换）。
3. 加入成功后双方属于同一局，先手随机决定，房主不固定先手。现行实现创建房间时即生成初始对局，加入后可行动，没有额外准备步骤。
4. 号码无效、房间不存在或满员时，说明原因，不悄悄改开另一种模式。

当前房主不会收到服务端主动语音通知。有屏设备可看状态更新；无屏房主在对方确认加入后说“战况如何”，获知开局状态和当前阶段。是否增加更自然的加入确认方式列为待决策。

### 5.3 战斗循环

```text
先手主动选择
  ├─ 蓄力 → 交给另一方主动选择
  └─ 攻击锁定 → 另一方响应 → 统一结算 → 检查胜负
                                              ├─ 结束
                                              └─ 未结束 → 另一方主动选择
双方各完成一次主动行动后进入下一完整回合
```

上图描述通常顺序；防守方真气为零时自动承受，不等待响应输入。每次攻击后的击倒立即结束，不等双方都行动。

示例以 A 抽到先手为前提，具体伤害由服务端返回：

| 步骤 | 玩家输入 | 体验中必须清楚的事 |
| --- | --- | --- |
| A 主动 | A：“强攻” | 已锁定攻击、已付真气，尚未命中，等待 B 响应 |
| B 获知局面 | 无屏时 B 可说“战况如何” | 对手发动什么攻击，现在需要自己响应 |
| B 响应 | B：“格挡” | 本次实际伤害、剩余气血、接下来 B 可主动出招 |
| B 主动 | B：“普攻” | B 的攻击已锁定，转为等待 A 响应 |
| A 响应 | A：“闪避” | 补上之前错过的结算，再处理当前响应；明确躲开或承伤 |

面对面时玩家可听见对方伙伴的公开播报，但不能把这种听见当作稳定的系统通知；有遮挡、噪声或不确定时应能查询。不能要求无屏玩家猜测对方何时已经操作。

### 5.4 胜负与再来一局

任一方气血归零后立即结束，双方从各自视角得到相反且一致的胜负结论，不再接受战斗行动。最后一次结算只返回给发起该次请求的设备，另一位无屏玩家仍需在下次发言时获取补账或查询终局。

当前“开始游戏”“再来一局”会新开单人局；在双人房中重开会撤掉旧房。继续和同一朋友对战的现有路径是重新开房、另一位重新加入，不能把它描述为已支持房间内再战。

建议后续增加双方同意的房间内再战，避免一方重开替另一方作决定；优先级取决于首轮试玩的重开频率和误操作情况。

## 6. 语音输入与反馈设计

### 6.1 指令与阶段

| 所处阶段 | 可执行的战术选择 | 其它可用输入 | 不能产生的效果 |
| --- | --- | --- | --- |
| 无对局 | 无现成战斗；首句招式可自动开单人局 | 开房、加入、开始游戏、问玩法 | 随意闲聊不能创建战斗或消耗资源 |
| 等待加入 | 无 | 查询、房间管理、问玩法 | 未加入对手前不能发动攻击 |
| 轮到自己主动 | 普攻、强攻、大招、蓄力 | 查询、问玩法 | 不能一次执行多个行动 |
| 对手攻击待自己响应 | 格挡、闪避、承受 | 查询、问玩法 | 不能把主动攻击当作防守响应 |
| 自己攻击已锁定 | 无新的战术选择 | 查询、问玩法 | 不能替对手响应，不能按响应结果换招 |
| 等对手主动 | 无 | 查询、问玩法 | 不能抢先推进回合 |
| 已结束 | 无 | 查询结果、按当前流程重开 | 不能继续伤害或重复结算 |

房间管理可能结束旧对局，不属于无副作用查询，应与战斗选择分开说明。

### 6.2 理解失败与歧义

| 玩家原话或情况 | 产品要求 | 当前状态 |
| --- | --- | --- |
| “强攻”“猛攻”及已支持的 ASR 误识别 | 归一化为同一行动，仍校验阶段和真气 | 已实现，词表与自由表达效果需真机验证 |
| “我的大招还剩几次” | 查询，不扣真气或大招次数；应回答次数 | 已阻止误出招；现有通用状态播报未专门回答大招次数，仍有信息缺口 |
| “不要大招” | 不执行，不把收手当成出招 | 已有拦截与提示，具体覆盖需持续验证 |
| “大招还是强攻” | 提示一次只选一种，不猜测执行 | 已有歧义拦截 |
| 没听清、未知说法、识别置信度不足 | 保持阶段，让玩家重说 | 已有兜底，不能用识别失败惩罚玩家 |
| 真气不足、大招已用、满真气蓄力 | 解释不合法原因，不改变战斗状态 | 已实现 |
| 慢请求返回时已换局或换房 | 不把旧结果写回新局，说明需要重说 | 已有串行处理与状态校验 |
| 网络重试带来重复行动 | 不允许同一已确认行动再次扣资源 | 作为验收要求；当前串行处理不等于完整的请求去重协议，尚需专项验证 |

### 6.3 伙伴播报原则

播报优先告诉玩家：行动是否生效、结果是什么、现在该谁说什么。采用短口语，常规回复以两句、60 字内为目标；补账与当前结果拼接后的总长度需单独检查，不能仅凭单段文案达标认定体验达标。

建议文案示例（不代表已替换现有文案）：

| 场景 | 示例 |
| --- | --- |
| 指令锁定 | “强攻已出手，等对手应对。” |
| 等待响应 | “对手发动强攻。格挡、闪避，还是承受？” |
| 识别失败 | “没听清，这次没有生效。请再说一次。” |
| 闪避失败 | “没躲开，受到5点伤害。轮到你出招。” |
| 查询大招 | “你还有一次大招，对手已经用过了。” |

伙伴可以有性格、回念唤出词和庆祝，但不能把“没躲开”说成“没听清”，不能提前宣布命中，也不能用角色表演盖住响应窗口。音效、灯效、动作不是当前已交付能力；如增加大招演出，主要演出应在防守选择完成后展开。

## 7. 公开信息与载体差异

双方气血、真气、大招剩余次数、轮次、当前行动方和待响应攻击属于玩家理解战况所需的信息。暴击和闪避结果在结算后公开，不能在对手选择响应前泄露。

| 信息 | 有屏载体 | 无屏载体 |
| --- | --- | --- |
| 双方气血、真气 | 现有沙箱通过快照和状态流展示 | 当前可查战况 |
| 大招剩余次数 | 状态快照已包含 | 应可按需获知；当前播报存在前述缺口 |
| 谁该主动或响应 | 当前状态及待响应攻击 | 通过回复或查询获知，不能假设会主动播报 |
| 对方操作后变化 | 状态流更新 | 当前等玩家下一次发言补账；问玩法等分支的补账覆盖需专项验收 |
| 第三轮起的增伤 | 玩家需要能理解伤害为何变高 | 现有播报会在部分回合提示，是否足够需试玩确认 |

`screen` 与 `voice` 是当前服务的载体能力区分。有屏客户端关闭补账播报，自行呈现状态；无屏设备默认保留补账。屏幕存在不代表玩家一直看屏幕，试玩需观察是否会漏掉关键结果。

## 8. 异常、换房与退出

| 情况 | 当前行为 | 建议设计或待决策 |
| --- | --- | --- |
| 房间号错误、房间满员 | 提示失败，原房间不变 | 反馈中清楚说明仍在哪场对局 |
| 主动加入新房 | 先验证目标房，再加入并撤旧房与旧局，清除双方补账 | 是否对正在战斗的换房增加确认，待试玩决定 |
| 对手换房或重开 | 原房间被撤，旧对局不再继续；无新对局时再说招式会开单人局 | 建议明确提示“对手已离开”，避免将 AI 当成原对手；当前无独立主动通知 |
| 一直不行动 | 无严格响应倒计时或超时判负，长期空闲后过期 | 提醒、默认响应和防拖延规则待决策，不临时增加回合硬截止 |
| 页面关闭、设备掉线、请求失败 | 尚无完整掉线判负与暂停恢复流程，内存局面受过期和服务重启影响 | 不应据此自动宣布另一方获胜；恢复体验须另行设计 |
| 玩家说认输或退房 | 尚无独立、完整的产品流程 | 建议确认意图后处理，退出和正常击倒分开记；认输判负规则待确认 |

不能把“设备身份在多轮对话间稳定”解释成已经具备断线恢复、重启恢复或掉线判负能力。请求失败时先查战况确认，不应引导玩家无条件重复一个可能已生效的攻击。

| P09 | 异步返回、重复与迟到输入 | 无旧局覆盖新局，无重复扣资源；分别验证，不用串行测试代替 | 服务专项 |

## 10. 首轮试玩与记录

沿用早期计划，建议 4 对玩家，每对练习后进行 4 局。记录实际抽到的先后手；在现有随机先手下不承诺自然形成均衡样本，需要对照先后手时另用可控测试环境。该规模用于发现体验问题，不能证明公平性。

每局记录：载体、单人或双人、双方经验、先手、结束轮数、总时长、有效战术输入数、重说次数、状态查询次数、阶段误判、人工提醒、补账长度、大招时机与落空后的反应，以及异常结束原因。已有日志能辅助核对，但这些统计尚未全部实现，不宣称已自动采集。

建议分别计算：

- 从加入成功到胜负明确的时长，和整局进入流程的时长。
- 每局重说与查询次数；将“没听清”“指令歧义”“规则不合法”分别记录。
- 无人工提示完成对局的局数，以及等待中不知道该谁行动的次数。
- 3～5 轮结束比例与按先后手分组的结果，只作为本轮样本观察。

试玩后询问玩家：是否觉得在指挥自己的伙伴，是否理解真气与后手生命补偿，为什么选择防守或承受，是否知道大招只可用一次，以及是否愿意立刻再玩一局。优先记录结构化事件、耗时和观察笔记；如需录音，另行确定采集方式。

## 11. 下一轮设计决策

| 决策 | 当前建议 | 作出决定所需的证据 |
| --- | --- | --- |
| 无屏设备何时通知下一位玩家 | 先验证面对面公开播报加主动查询能否完成一局 | 加入、响应、终局是否频繁需要人工提醒 |
| 针对状态的简短回答 | 优先补齐大招次数等具体查询 | 现有查询信息缺口及玩家常问的问题 |
| 双方准备确认 | 暂不改现有加入即开打路径 | 玩家是否经常尚未准备好就开始，是否容易误入 |
| 房间内再来一局 | 候选改进，需要双方同意 | 试玩中的再战意愿、重新配对成本和误开单人局次数 |
| 退出、认输与掉线 | 分开定义结果，暂不引入自动判负 | 真实中断类型、持续时间、玩家能否理解恢复或结束 |
| 伙伴性格、台词与演出 | 先保证阶段和结果清楚，再加短表现 | 玩家对伙伴感的评价、台词是否遮挡操作 |

这些是建议的产品决策顺序，尚未形成新增开发承诺。当前阶段优先跑通并验证双人体验，再根据问题决定是否改流程或数值。
