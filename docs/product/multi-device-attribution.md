# 共鸣：闻声对决 · 串音与指令归属

[返回产品设计总览](product-design.md)

日期：2026-10-24。状态：本文件描述已实现的服务端兜底能力与默认关闭的可选策略；真机验收未完成，未交付部分单独标明。

两台设备距离近、都没有屏幕时，服务端会收到不属于自己的话：对手的指令、自己或对手刚被朗读出来的播报。玩家看到的是“我还没说话，伙伴就动了”“它把我刚听到的那句又念了一遍”。本文件说明服务端做到哪一步、靠什么判断，以及哪些问题不在服务端能力范围内。

## 1. 现象与责任边界

同场故障有三类，成因不同，处理方式也不同：

| 现象 | 直接原因 | 服务端能做 | 服务端不能做 |
| --- | --- | --- | --- |
| 对手的指令被本机执行 | 两台设备共用一个智能体，收到的是同一路原话 | 认出“这句不是冲我来的”，当场收住 | 判断声音来自哪台设备 |
| 自己的播报被当成玩家原话再执行一遍 | 朗读退回麦克风，形成回灌 | 认出“这是播报，不是玩家的话” | 阻止平台把朗读送进麦克风 |
| 同一条结算被反复播报、长提示被越念越长 | 回灌的提示语又被当成新输入 | 命中回灌时只回极短应答，切断循环 | 提供平台级回声消除 |

平台侧没有回声消除，也不会在收到原话时告诉我们说话人是谁；真正把身份钉住的方案是“一设备一智能体、各绑各的声纹”，属于平台配置，由调研分支维护（`docs/engineering/platform-voice-capabilities.md`、`docs/references/voice-attribution-research.md`，合入前此处不建立链接）。本文件只描述服务端兜底，不假设平台能力，也不替代平台侧配置。

因此服务端的两条防线，一个是内容层的（回灌识别），一个是流程层的（座位口令），都建立在同一个前提上：**服务端只根据文本和房间座位判断，永远不知道麦克风前站着谁。**

## 2. 当前回灌识别

以下是当前文本协议的防线与实际文案。v2 目标让伙伴自由表达，服务端看不到最终播放句子，旧句式规则的覆盖会缩窄；不能继续把“认出旧播报”解释成识别所有演绎。本分支 v2 命中静默时返回 silent，沙箱不再生成占位话术；平台仍须配套验证。迁移与真机边界见 [实施说明](../engineering/mcp-v2-migration.md)。

判定依据是播报文本的结构特征，不是按句子逐条硬编码：结算数字与资源变化、阶段提示、编号播报、结局与补账话术、“等对手应对”“该我出招”这类交接句、第二人称叙述（“你已经出手了”“轮到你出招”），以及结局句式。真人正常报招式（“普攻”“我出大招”“我要闪避”）不会被判成回灌；先报自己的数值、再补一句明确招式（“我还有14点生命值，普攻”“我还有14点生命值普攻”）按指令处理，不依赖 ASR 是否给了逗号，招式用“攻击”这类别名也算，只有数值半句单独出现时才当播报；口语里常见的“轮到我”也不再单独算回合提示，认的是播报里的“轮到我出招”“轮到你出招”。

命中后一律只回一句极短应答「嗯。」，不推进对局、不消耗生命值或能量、不重复播报内容；同一台设备两秒内连续收到回灌时不再出声，避免“回答又被收进去”的循环。

取舍写在明处：规则宁严勿松，代价上限是玩家少听一句提示，不会动资源；宁可漏掉一次真话也不误伤一次真招。真机日志里出现过“对手一记普攻”“你已经出手了，等对手应对。”“轮到我们了，大招。”这类被回灌的句子，按上述特征都能认出来；而“我出大招，接招！等对手应对。”和“我出大招，接招！”这种回灌句的变体同样能识别。

## 3. 他机指令降噪（已实现）

双人房里，本机不是当值方（等对手主动，或自己已经出招、正等对手应对）时，原来的长提示（“该我出招了，可以说普攻、强攻、大招或蓄力”）本身就会被念回麦克风。现在这两种情况只回一句最短事实：「还没轮到我出招。」「这一手等对手应对。」

单人局不受影响，仍是原来的阶段提示。

## 4. 座位口令（已实现，默认关闭）

轮次仲裁挡不住最要命的一类串音：**当值设备收到对手的话**。A 正该出招，B 在旁边喊“大招”，A 是当值方，服务端没有任何理由拒绝——这句话在文本层面完全合法。

服务端的显式解法是让玩家自己说明“这句话是替谁说的”：

- 环境变量 `ATTRIBUTION_MODE`，取值 `off`（默认）或 `strict`。
- `strict` 时，双人房两个座位各有一个短口令：**发起方是红方，接受方是蓝方**。口令按房间座位分配，与设备无关，换座位就换口令。
- `off` 时完全不生效，行为与引入前一致。

`strict` 下的判定：

| 玩家这句话 | 处理 |
| --- | --- |
| 带自己的座位口令（“红方大招”“蓝方格挡”） | 口令只是标签，摘掉后照常读招式，规则不变 |
| 带对方的座位口令（本机红方，听到“蓝方大招”） | 静默丢弃：不执行、不推进对局、不回复任何文本 |
| 两个口令都带 | 以自己报的为准，摘干净后再读 |
| 只报口令、没说招式（“红方”） | 回一句自报座位的确认：「红方这边，我在听，说招式就行。」 |
| 什么口令都不带 | 沿用原来的轮次仲裁，当值方才执行 |

口令词与招式解析互不干扰：`红方` 单独说不会被读成任何招式，`红方大招` 照样拆出“大招”。口令是可选的归属标签：报了就按座位判、不报就沿用轮次仲裁，所以演示时用 `ATTRIBUTION_MODE=strict` 启动服务，玩家只需要在自己这台说话时顺口带上座位号——不必每句都念。

**边界必须说清：口令只解决“替谁说”，不解决“谁在说”。** 邻居不报名号直接喊一句“大招”，当值设备仍会执行——服务端无法分辨两个声音。所以 `strict` 是演示期可选的降噪手段，不是身份认证；要根治仍得靠平台侧一设备一智能体加声纹。选“静默不回”而不是“回一句提醒”，是因为任何回一句都会被设备再收一遍，又变成新的串音。

## 5. 与播报纪律的衔接

新增文案都遵守既有约束：第一人称“我”、对方称“对手”、一句到两句、60 字内、不带 Markdown 与表情。

当前文本协议的反馈示例（不是 v2 的固定话术；静默路径也不是伙伴发言）：

| 场景 | 文案 |
| --- | --- |
| 命中回灌 | 嗯。 |
| 双人房等对手主动 | 还没轮到我出招。 |
| 双人房已出招等对手应对 | 这一手等对手应对。 |
| 严格模式只报了座位号 | 红方这边，我在听，说招式就行。（蓝方同理） |

固定自称只出现在最后一句：这是玩家最容易疑惑“这是哪台在说话”的纠错场景。普通出招播报不加，避免每条回复都变长。

## 6. 未交付与待验证

- **真机同场验证未完成。** 上述行为来自仓库测试与本地双人房脚本，不代表两套硬件同桌时的实际效果。
- `strict` 模式的可用性取决于对手速记口令，以及 ASR 是否稳定识别“红方/蓝方”。口令被识别成别的词时，这句话会退回普通发言。
- 座位口令的触发条件（只认发起方/接受方）尚未经过真实演示检验；是否需要自定义口令、是否需要更多座位（三人以上观战）都未定。
- 平台侧声纹与拆智能体尚未合入，两者与本方案的关系（谁兜底、谁优先）等调研分支落地后再定。
- 状态播报目前不自报座位，是否需要同样处理待试玩确认。
- 没有「二次确认」环节：命令路由只接受置信度 ≥ 0.6 的结果，低于阈值一律按没听出来处理，不会反问「你是想放大招吗」。这么做是为了避免语音上多一轮往返，代价是模糊说法要玩家再说一遍。

## 7. 验证范围

仓库测试覆盖以下口径（命令见根目录 README）：回灌识别对播报语料与真机日志原句的判别、真人报招式不误判、命中后不推进对局不耗资源、连续回灌不重复播报；`strict` 模式下当值设备带自己口令正常出招、收到对方口令静默、双方都不带口令沿用原仲裁；`off` 模式与基线一致；单人局不受影响。真机串音仍需现场验收，仓库测试不能替代。
