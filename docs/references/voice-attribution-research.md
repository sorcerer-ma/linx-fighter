# 双设备串音的指令归属：方案对比与推荐

> **给决策者的一句话**：首选「**一设备一智能体 + 各绑各的声纹**」——这是唯一能让平台门禁真正变成座位归属、且**游戏侧代码不用改**的配置；代码侧今晚配套「轮次仲裁话术 + 状态播报/固定自称 + 座位口令」，把剩下那部分降成可理解的摩擦。声源定位（DOA）与蓝牙式多设备仲裁在硬件和链路上都不成立，直接否掉。

日期：2026-10-24。范围：只做「选哪条路」的对比与推荐。平台 API 的参数细节不在这里重复，见灵犀平台文档与并行的《平台语音能力》调研；本文引用的平台行为以那份调研已核实的一手事实为准。

## 1. 串音不是一种病：四类失败，证据强度不同

先把"B 说的话被 A 执行"拆开。它们成因不同、解法不同，混在一起讨论就会选错方案。

| 编号 | 现象 | 证据 | 后果 |
| --- | --- | --- | --- |
| **F1 错归属执行** | B 说「大招」，A 收到并**成功结算** | 用户在真机上口述；我们手上的日志没有直接抓到这一条 | 结算错人、两人状态不一致，最伤 |
| **F2 归属错但被拒** | B 的话落到 A，A 的轮次/阶段不允许 → 回「你已经出招了，这一手等对手应对」 | 日志实证（见 `SHARED/SHARED-CONTEXT.md` 第 3 节：两台交错出招后，另一台说「硬扛」被这样回） | 指令凭空消失，B 以为自己说了 |
| **F3 自播报回灌** | 我们自己的 TTS 播报被麦克风收回去，当成玩家原话 | 日志实证（同一节：回灌进来的原话就是「对手一记普攻」「你已经出手了，等对手应对。」「轮到你出招」「主动阶段可以说普攻、强攻、大招或蓄力。犀利」「轮到我们了，大招。」） | 幽灵指令，最伤且最容易被误判成"玩家乱说" |
| **F4 旁人/环境** | 房间外的人、电视、手机外放 | 推断，未单独验证 | 误唤醒与误触发 |

**证据强度必须区别对待**：F2、F3 有日志实证；F1 只有用户口述、需要在真机上复现（见第 8 节）。只按 F1 设计会过度工程化；忽略 F3 会把最吵的那类问题留到现场。而 F3 已经不是"偶发 bug"——平台侧没有回声消除入口（见 2.2），它是结构性的。

## 2. 两个关键发现

### 2.1 引擎已经挡住了一半的错归属

读代码和日志能看出，`engine.ts` 已经用「轮次 + 阶段」做了隐式仲裁：

- 轮到 A 出招时，B 的话如果落到 A 上，而 B 说的是应对动作（格挡/闪避/承受）→ 阶段不对，被拒（这正是 F2）。
- 反过来，**真正挡不住的是另一种**：A 当值，B 在 A 旁边说「大招」——A 是当值设备，服务端没有理由拒绝，于是替 A 打出了这一手。这就是 F1。

也就是说：**现有引擎能挡住"非当值设备收到的话"，挡不住"当值设备收到了对手的话"**。

再往下一层看 F1 的成因。B 为什么会在大招该 A 出的时候说「大招」？因为**无屏，B 不知道现在轮到谁**（用户原始诉求第 3 条原话就是"硬件无屏、状态不同步"）。所以：

> **归属问题的一半其实是状态可见性问题**：状态在服务端是已知的（`active`），而两台设备相距 1-2 米、彼此都能听见对方的播报——这条"空气信道"是免费的广播通道。

这也是本文推荐里最便宜的一块：让"该谁说话"变成两台设备都能听见的声音，比让机器分辨"谁在说"容易一个数量级。

### 2.2 F3 是结构性问题，不是一个待修的 bug

平台侧已核实的事实：

- **没有 AEC / 回声消除 / 降噪的配置入口**；
- **没有「最近说话人优先」这类策略**；
- **没有音频透传或旁路**：透传通道只承载 JSON，给 MCP 的只有文本；
- 唤醒词在设备端，平台只管"唤醒后是否问候"；收音窗口由 `listen.start` / `listen.stop` 控制，**默认时长文档未给（未确认）**。

四条合起来意味着：设备自己的播报只要落在收音窗口内，平台就会照常送去 ASR、照常当成玩家输入。我们在服务端既听不到音频、也没法让平台"听到播报时闭嘴"。F3 只能从两头堵：**平台门禁（声纹）** 或 **服务端文本去重（认出这是自己的话）**。这也是为什么第 6 节把声纹放在首选的位置——它顺带能压 F3（推断，需实测）。

## 3. 约束清单：哪些路一开始就堵死

| 约束 | 来源 | 对选型的影响 |
| --- | --- | --- |
| 无屏，只有一条语音通道 | 产品定位 | 所有反馈只能靠播报；误判代价被放大 |
| 两台设备**共用一个 agentId**（`447ae9…6002`） | 现场诊断 | 声纹绑定是智能体级的 → 两人都算"主人"，门禁形同虚设 |
| MCP 请求头只注入 `X-Linx-Device-Id / Agent-Id / Session-Id` | [平台 MCP 接入文档](https://linx.qiniu.com/docs/xrobot/mcp/software-mcp) | **说话人身份只喂给平台自己的大模型，不进工具入参**；服务端拿不到"是谁" |
| 平台无 ASR 热词 | 平台调研（已核实） | 「红方/蓝方」的同音纠正只能在我们侧做（复用拼音表） |
| 平台无音频透传/旁路，给 MCP 的只有文本 | 平台调研（已核实） | 自建声纹、DOA、波束成形全部没有输入 |
| 平台无 AEC/降噪入口，无「最近说话人优先」 | 平台调研（已核实） | F3 结构性（2.2）；云侧"抢答退避"也无处可配 |
| 唤醒词在设备端，收音窗口 `listen.start/stop`（默认时长未确认） | 平台调研 | 端侧行为我们不可控，只能靠门禁与文本层兜 |
| 1-2 米、同一房间 | 现场 | 空气信道共享：串音双向，播报也互通（双刃） |
| 五工具契约，身份只从请求头解析 | `AGENTS.md` | 不能把 speaker/座位塞进工具参数，只能在服务端从文本里读 |
| 服务端已知 `active`（该谁出招） | `src/game/engine.ts` | 轮次仲裁是现成的，不需要新信息 |

## 4. 七个方案逐个评

### 4.1 声纹识别（平台声纹 V2）

**一句话结论：可用，但不可编程——它能过滤人，不能告诉我们"是谁"。**

**原理**：把一句话映射成说话人嵌入向量（x-vector、ECAPA-TDNN 是这条线的代表工作），与注册样本算相似度，过阈值就判"是他"。平台把这层做在内部，对外只给 `speaker_id` 和"只回应指定的人"这个开关。

**平台实际怎么工作**（已核实）：开启「仅回应已添加说话人」后，**命中就正常回复，不命中平台直接把这句话丢掉、不转发**。所以对我们服务端来说，被挡掉的话表现为「这句话从来没有发生过」——它是**静默**的。无屏场景下这很危险：玩家只会觉得"机器坏了"，没有任何可读的负反馈。

**决定性限制**：声纹是**门禁**，不是**标签**。MCP 三个头里没有 speaker 字段，说话人身份只喂给平台自己的大模型。于是三种配置的后果完全不同：

| 配置 | 门开给谁 | 结果 |
| --- | --- | --- |
| 一个智能体 + 绑两位玩家声纹（**现状**） | 两个人都算主人 | 门等于没有：串音照旧（F1 不受影响），只挡得住旁人（F4） |
| 一个智能体 + 只绑一位玩家 | 只有一个人 | 另一个人在自己设备上也被挡 → 双人局没法玩 |
| **一台设备一个智能体 + 各绑一方** | 每台设备只认自己那个人 | **真门禁：B 在 A 旁边说话，A 不响应**（F1 被挡住） |

**顺带的效果**：设备自己的 TTS 语音不属于任何已注册声纹，按上面的门禁行为**推断**也会被挡掉 → F3 可能同时被压住。这是推断，必须在真机上验证（第 8 节），不要当成已解决。

**误判与体验代价**：远场 + 混响 + 音量变化会让误拒/误受都上升——INTERSPEECH 从 2020 年起专门设了[远场说话人验证挑战赛（FFSVC）](https://arxiv.org/abs/2005.08046)，说明"隔一两米说话"本身就是难题；感冒、语速、老人/孩子嗓音差异都会掉分。误拒时无屏用户**得不到任何提示**，比说错更难排查。

**平台侧细节**（结论级，见[声纹识别 V2 API](https://linx.qiniu.com/docs/xrobot/api/voiceprint-v2)）：以 speaker 为中心；一个说话人只维护一条默认声纹，重建即覆盖；注册要一个平台可访问的 `audio_url`（可选 `source_device_id`）；接口不返回特征向量；智能体需绑定 `speaker_ids`；开关在 `extra.voiceprint.chat_only_enabled`（`speaker-config` 里只读，改走智能体 API）。

**工作量**：纯配置，代码 0。现场注册（安静单人样本 + 公网可访问音频 URL）约每人 10-20 分钟（估算）。双智能体方案另加一套提示词/音色的维护成本。

**今晚能否**：**能**（配置侧）。这是本轮唯一"代码零改动、同时覆盖 F1+F3+F4"的路子，详见 6.1。

### 4.2 座位口令 / 呼叫词（「红方，大招」）

**原理**：把归属编码进语言，服务端解析前缀并与座位比对。它判的是"**替谁说**"而不是"**谁在说**"——这一字之差正是它比声纹更适合兜底的地方：座位在服务端是确定的（`rooms.byPlayer`、`deviceId`），不需要任何新的感知能力。

**要求**：无硬件依赖、无平台依赖。只改 `src/game/command.ts` 的解析层，与现有唤出词、招式别名同层。

**误判与代价**：

- 每句话多 2-3 个字；单人局应默认关闭。
- 「红方/蓝方」会被 ASR 同音误识别（如"宏方"），而**平台没有 ASR 热词**，纠正只能在我们侧做 → 复用 `asr` 分支正在做的拼音容错表。
- 优先级必须定死：**座位口令前缀 > 唤出词 > 招式别名**，否则"红方，大招"可能被当成未知输入。
- 挡不住两人故意冒充对方，但面对面场景无意义。

**工作量**：低，1-2 小时（含测试）。

**今晚能否**：**能**，建议作为双人局的默认开启项。

### 4.3 轮次 / 时序仲裁

**原理**：服务端已经知道 `active`。非当值设备送来的输入不结算，改为明确引导。

它能做三件事：

1. **把 F2 的话说清楚**：现在回「你已经出招了，这一手等对手应对」，玩家听不懂"谁"；改成「现在轮到对手，请在他那台机器上说」——同样不消耗资源、不推进阶段。
2. **给状态播报找时机**：当值方播报"该我了"，两台设备都听得见，等于免费的空间提示（2.1）。
3. **收窄 F1 的判定条件**：它挡不住"当值设备收到对手指令"，但能保证"非当值设备上的任何输入都不产生结算"，避免错误叠错误。

**关于"抢答退避"**：这需要平台层有"最近说话人优先"或就近唤醒一类的策略，**平台没有这个配置**（2.2 已核实），云侧也无从获取"另一台听得多清楚"。唯一可做的等价物就是服务端仲裁——同一时刻只认一台设备的一次输入。

**误判与代价**：站位与座位不一致时（两人都挤在一台机器前），"请到另一台机器说"会加重摩擦；也可能让人觉得被机器管着。属于话术问题，可调。

**工作量**：低，2-3 小时（含测试）。

**今晚能否**：**能**，兜底首选。

### 4.4 声源定位 / 波束成形（DOA）——否

**硬件要求**：多麦克风阵列 + 端侧做 DOA/波束成形 + 固件把方位角上报；平台还要把方位角暴露给业务。

**本项目现实**：

- 平台文档的 API 导航里**没有**任何方位角/波束/阵列接口，MCP 头也只有 device/agent/session 三个字段 → **不具备可用通路**（这一条是确定的）。
- 两台真机的型号与麦克风数量：平台文档（含硬件/固件篇）**均无记录**，`SHARED` 里也没有 → **待确认**。本文不假设它们有阵列。
- 本项目跑在[开源小智固件](https://github.com/78/xiaozhi-esp32)的硬件生态上；该仓库支持从 ESP32-C3 到 ESP32-S3 的多种板卡（README 写"当前矩阵 171 个变体"，部分开发板如 ESP32-S3-BOX-3 是多麦的）。但**"某些板子有多麦"不能推成"我们手上这两台有多麦"**。

**即便硬件具备，也不建议**：两人相距 1-2 米、与设备夹角通常小于 30°，室内混响下方位分辨率不足以稳定区分两个人；更致命的是**服务端根本不接触音频**（平台无音频透传），DOA 结果即使算出来也没有通路进业务。真要做只能在端侧做门禁，那是换硬件的项目，不是今晚的项目。

**结论**：否掉，不作为本轮方案。只有"换带阵列的设备 + 端侧做门禁"时才重新评估。

### 4.5 多设备唤醒仲裁（小爱 / 天猫精灵 / HomePod / Amazon Echo）

**原理**：一个房间里多台同类设备同时听到唤醒词时，只让一台应答，避免多台一起说话。业内成熟做法是**设备间短距通信互报 + 各自评估唤醒质量**，然后选一台。

**Apple 官方描述**（[How Siri works with multiple devices](https://support.apple.com/en-us/105077)）：多台设备"用蓝牙互相通信"来决定谁响应，选中的是"最听清你的那台，或者刚被拿起/刚用过的那台"；如果蓝牙关闭或设备不在蓝牙范围内，"可能会有多台设备响应"。

**Amazon**：Echo Spatial Perception（ESP）让多台 Echo/Dot 协同，只由一台应答，用于提升响应速度并减少设备间冲突（[Wikipedia: Amazon Echo](https://en.wikipedia.org/wiki/Amazon_Echo) 转述）。

**小爱 / 天猫精灵**：两家在消费级产品上都提供过用户可见的「就近唤醒」能力（多台同时被叫到时由就近的一台应答）。公开资料以用户手册与社区帖为主，**未见官方算法说明**，这里只作为"同类问题确实需要专门机制"的旁证，不作为技术依据。

**能不能借鉴到我们这两台设备**：借不了机制，只能借原则。这套做法的两根支柱是（a）设备之间的通信信道、（b）每台设备自己算出的唤醒置信度。我们的两台设备之间没有这条链路，云端也拿不到"另一台听得有多清楚"——平台只会把胜出那台的结果送进来，而且**平台没有就近唤醒/最近说话人优先的配置项**。**可以借的只有一条产品原则：同一时刻只允许一台设备应答**，在我们的架构里用服务端轮次仲裁模拟（4.3）。

### 4.6 视觉 / 物理辅助

用户明确说无屏，屏幕方案不讨论。剩下值得保留的只有**物理标识**：机器上贴"红方 / 蓝方"贴纸，或用一句播报 + 一盏灯区分。成本≈0，收益是让玩家一眼知道"该对着哪台机器说话"。NFC/二维码需要每次碰一下，对局中频繁操作不现实，不推荐。

### 4.7 产品层规避

| 做法 | 怎么做 | 成本 | 注意 |
| --- | --- | --- | --- |
| **固定自称** | 开局/换边/被误叫时播一句「我是红方，听你指挥」 | 0.5-1 小时 | 播报硬约束：第一人称、单条两句 60 字内；**不要每条都加**，否则吃掉正文长度 |
| **轮流说** | 回合制天然轮流，只需把"该谁"用可听见的方式给出来 | 与 4.3 合并 | 两台设备能听见彼此播报，这是免费的广播通道 |
| **开战确认** | 每台设备报座位名，玩家回一句「红方就位」，建立 设备↔座位↔人 的锚 | 1 小时 | 换边、换人、接受挑战后要能重来一次；也是双智能体方案的成本检测点 |
| **物理标识** | 贴纸/灯 | 5 分钟 | 见 4.6 |

## 5. 冲突矩阵：每个方案到底解决哪一类

「高」= 直接解决；「中」= 能降级或部分覆盖；「无」= 不解决。

| 方案 | F1 当值设备收到对手指令 | F2 被拒但没提示 | F3 自播报回灌 | F4 旁人/环境 | 落地节奏 |
| --- | --- | --- | --- | --- | --- |
| 声纹：单智能体绑两人（现状） | 无 | 无 | 高（推断，待实测） | 高 | 今晚可做 |
| **声纹：一设备一智能体各绑一方** | **高** | 无 | 高（推断，待实测） | 高 | **今晚可做（配置）** |
| 座位口令 | 高 | 中（能说"这不是你的座位"） | 无 | 无 | 今晚可做 |
| 轮次/时序仲裁 | 无 | **高** | 无 | 无 | 今晚可做 |
| 状态播报（并入仲裁） | 中（消除"不知道轮到谁"这个根因） | 高 | 无 | 无 | 今晚可做 |
| 抢答退避（平台层） | — | — | — | — | **平台无此配置，不可行** |
| DOA / 波束成形 | — | — | — | — | **否** |
| 多设备唤醒仲裁（借机制） | — | — | — | — | **不可借用** |
| 物理标识 + 固定自称 | 中（减少"对着错机器说"） | 中 | 无 | 无 | 今晚可做 |

**读法**：没有任何单一方案覆盖全表。F1 只能靠双智能体声纹或座位口令；F2 只能靠仲裁话术；F3 靠平台门禁（需实测）；F4 只有声纹。所以结论必然是组合，而且**其中最重的一块（F1+F3+F4）恰好落在"不改代码"的配置侧**。

## 6. 推荐组合

### 6.1 首选（今晚可做，配置侧）：一设备一智能体 + 各绑各的声纹

**为什么首选**：现状是两台设备共用一个 `agentId`，于是"只回应指定的人"这道门对两个人同时开着，等于没有。拆成两个智能体、各绑各的声纹后，门禁就从"平台层的过滤器"变成"**座位归属判定**"——B 在 A 旁边说话，A 设备直接不响应。而且**游戏侧代码一行都不用改**：对局键仍是 `deviceId#agentId`，房间仍按房间号索引，两个智能体连的是同一个自建 MCP 服务。

**配置步骤**（约 30-60 分钟，不含现场注册声纹）：

1. 新建第二个智能体（乙），复制甲的全部配置：同一个 MCP 服务地址、同一份提示词、同一套音色（音色不同反而增加玩家困惑，建议一致）。
2. 用官方接口把设备切到目标智能体：`PUT /v1/devices/{mac_address}/agent/{agent_id}`，把 `e8:f6:0a:8c:56:6c` 指到甲、`e8:f6:0a:8b:f4:b4` 指到乙（[设备 API](https://linx.qiniu.com/docs/xrobot/api/device)）。
3. 在甲上绑定红方声纹、在乙上绑定蓝方声纹（`speaker_ids` 只放一个），两边都打开「仅回应已添加说话人」。
4. 各自确认智能体的 `extra.voiceprint.chat_only_enabled` 生效（`speaker-config` 是只读的，改要打智能体 API）。
5. 按 4.7 加一句开战确认，让玩家知道"我说话的是哪台"。

**回滚方式**：三步都能单点回退，且互相独立——把设备指回同一个 `agent_id` 即恢复现状（`PUT` 同一个接口，幂等）；关掉 `chat_only_enabled` 即关掉门禁；声纹绑定解除不影响对局逻辑。**建议在演示前先拍一次回滚**，确认"改回去能立刻恢复昨天能用的状态"。

**验证方法**：

- **日志验证（最快）**：同一局里两台设备的请求头 `X-Linx-Agent-Id` 应该**不同**。用 `ssh linx-fighter-las` 看结构化日志里每个 `game_say` 调用的 agent 头，一局之内出现两个不同值 = 配置生效。
- **绑定验证**：两台设备分别对可控文本说话，确认只有绑定的那个人能被响应。
- **功能验证**：完整打一局，确认发起挑战、接受挑战、出招、结算、播报全链路没有退化（重点是房间索引和补账，因为它们依赖身份）。

**真机判定标准**（这条最关键）：**B 站在 A 设备旁说「大招」，A 设备不响应**（既不结算、也不误报"轮到你"）。同时 **B 在自己设备上说话仍然正常**——两条都满足才算成功；只满足前者说明门禁把两个人一起挡了。

**风险与未确认项**：两个智能体要各配一次同一个 MCP，是否会话/并发有限制——**需要确认**（附录 B 的 B4）；提示词、音色变成两份，改一处要改两处；换边要重新绑定，现场成本增加；如果平台对"同一 MCP 被两个 agent 调用"有限制，这条首选会退化（退化为 6.2 的三件套）。

### 6.2 今晚配套（代码侧）：三件套

1. **轮次仲裁与引导语**（4.3）：非当值设备的输入不结算，话术改成"现在轮到对手，请在他那台机器上说"；当值方播报"该我了"。
2. **状态播报 + 固定自称**（4.7）：开局每台设备报一次座位名，之后只在换边/被误叫时说；保持现有长度纪律。
3. **座位口令**（4.2）：双人局开启，前缀容错复用拼音表。**这是当 6.1 因平台限制无法落地时的兜底**，也是唯一能在"当值设备收到对手话"时用纯代码兜住的手段。

### 6.3 演示后做（P1）

1. **向平台提一个需求**：MCP 请求头带上说话人（`X-Linx-Speaker-Id` 之类），或允许把 speaker 绑定到设备。有了这个字段，声纹立刻从"过滤器"变成"标签"，归属判定可以在服务端一次做对，比我们绕任何弯都有效。
2. **F3 端侧核查**：`listen.start/stop` 的收音窗口默认行为、端侧 AEC 能力。若端侧本应做回声消除，那是配置或固件问题，比在服务端做文本去重更根本。
3. **双智能体的换边自动化**：现在换边要人工重绑，做成脚本后现场成本才可接受。

### 6.4 明确不做

- **DOA / 波束成形**：平台无通路（确定），硬件是否有阵列待确认（4.4）。
- **照抄蓝牙式多设备仲裁 / 抢答退避**：没有设备间信道，平台也没有就近唤醒配置（4.5）。
- **把 speaker/座位塞进工具参数**：违反"身份只从请求头解析"的硬约束。
- **NFC / 二维码碰一碰**：对局中操作成本过高（4.6）。

### 6.5 两种不推荐的做法

- **只上声纹、不动智能体结构**：单智能体下门对两个人同时开着，串音一点没改善（最多挡旁人 + 可能压 F3）。这是最容易在演示前踩的坑——"配了声纹以为解决了"。
- **只上仲裁**：能消除 F2 的困惑，但挡不住 F1——A 当值时 B 在 A 旁边说「大招」，A 照样出招。

## 7. 落地边界：代码侧 vs 配置侧

本轮写作用域约定：`src/game/service.ts` 归 `intent` 独占，`attribution` 只动 `src/game/crosstalk.ts`（新）、`src/game/command.ts`、`src/game/narrator.ts`。

| 事项 | 类型 | 入口 | 节奏 | 估时 |
| --- | --- | --- | --- | --- |
| 一设备一智能体 + 声纹绑定 | 配置 | 设备 API + 控制台/智能体 API | **今晚可做** | 30-60 分钟 + 现场注册 |
| 座位口令解析与座位比对 | 代码 | `src/game/command.ts` | **今晚可做** | 1-2 小时 |
| 串音/回声判定（含 F3） | 代码 | `src/game/crosstalk.ts`（新） | **今晚可做** | 2-3 小时 |
| 引导语、固定自称、状态播报 | 代码 | `src/game/narrator.ts` | **今晚可做** | 0.5-1 小时 |
| 提示词补座位话术 | 配置 | 控制台智能体提示词 | **今晚可做** | 10 分钟 |
| 双智能体换边自动化 | 代码/脚本 | 运维侧 | 演示后做 | 半天 |
| MCP 头带 speaker | 需求 | 平台 | 演示后做（外部依赖） | — |
| F3 端侧 AEC 核查 | 排查 | 端侧/平台 | 演示后做 | 未评估 |
| DOA / 多设备仲裁 | — | — | 不做 | — |

**建议的判定顺序**（给命令层/串音层；每一步都不能消耗能量或推进阶段）：

1. **回声命中**：与最近 N 条播报文本做规范化相似度（容忍 ASR 错字）→ 丢弃，最多回一句极短提示。
2. **座位口令解析**：解析出的座位与 `deviceId` 所属座位不匹配 → 不结算，引导到正确设备。
3. **非当值设备**：不结算 + 明确引导（现有行为，只改话术）。
4. **正常**：走原有流程。

前三步都要有"不消耗资源、不推进阶段"的边界测试；前缀解析覆盖空串、单字、全角、大小写、同音误识别。

**注意分工**：声纹与设备绑定是配置侧的活，不涉及代码；`crosstalk.ts` 的回声判定与声纹门禁无关（门禁在下游，我们只做文本层面的兜底），两者不要混在一个判定里。

## 8. 风险与真机验证清单（对齐验收项 P10）

现有[验收清单](../product/acceptance-and-playtest.md)里 P10「同室语音与长播报」已经点了这一项，下面是可以直接照着做的记录口径。

| 要测什么 | 怎么测 | 判定 |
| --- | --- | --- |
| **双智能体是否真的生效** | 一局内看两台设备的 `X-Linx-Agent-Id`（`ssh linx-fighter-las` 结构化日志） | 同一局出现两个不同值 |
| **门禁是否只挡外人** | B 站 A 旁说「大招」；B 在自己设备上说「大招」 | 前者 A 无响应，后者 B 正常响应（两条都满足才算成功） |
| F1 是否真实存在、比例多少 | 两人相距 1-2 米，轮流在"不该自己说"的时机说「大招」，各 20 次 | 计三分类：正确拒绝 / 错误执行 / 被吞 |
| 座位口令的 ASR 稳定性 | 「红方，大招」「蓝方，格挡」各 20 次，含正常/偏快/偏轻三种音量 | 前缀识别率、整句成功率 |
| 声纹在 1/2/3 米的接受率 | 同句在三个距离各说 10 次 | 接受率曲线；区分"听到但被拒"与"根本没唤醒" |
| 声纹能否挡住自己的播报（F3 假设） | 开关前后统计回灌次数 | 回灌次数是否显著下降 |
| 门禁误拒的可感知性 | 故意未绑定的嗓门说一句，看玩家多久发现 | 记录"以为机器坏了"的次数；决定是否要端侧提示 |
| 引导语是否被听懂 | 被拒后问玩家"刚才机器为什么没理你" | 主观 1-5 分 + 记录原话 |
| 换边/换人成本 | 中途把两人座位互换，计时恢复 | 分钟数；是否可接受 |

**还缺的证据**（本轮无法验证）：两台设备的麦克风数量与端侧是否有 AEC（**待确认，不要臆测**）；两个智能体共用同一 MCP 是否有限制；`listen.start/stop` 默认收音时长。都列进附录 B。
